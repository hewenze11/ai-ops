# §52 并发与等待（2026-10-23）

用户提出的两个场景：

1. **批量排查**：一台主服务控制 100 台机器，整体宕机时要逐台上去看。要求同时调工具、一起取数、汇总处理。
2. **并行等待**：大任务里嵌套一个十几分钟的构建，其余工作照常推进；要轮询工具；要能"等"或"不等了直接返回"。

下面把"现在为什么不行""怎么改""哪些边界不能动"讲清楚。

---

## 52.1 现状：三重串行

| 层 | 位置 | 限制 |
|---|---|---|
| 模型层 | `turns.py` | `if len(calls) != 1: raise` —— 一次只能发一个工具调用，多发判失败 |
| Agent 层 | `agent.py` | `while True: worker.once()` —— 同步执行到底，执行期间不 claim |
| 轮次层 | `app.py` claim SQL | 同轮次内前序任务未完成，后续任务不派发 |

三层任意一层都会让并行失效。

**Agent 层已改（§52.2），扇出已做（§52.4），等待原语已做（§52.5）。只剩同轮次只读 FIFO（§52.7 第 4 项）。**

---

## 52.2 Agent 层：已完成

用户原话的设计：

> 同一个主服务发出去的命令，在执行 Agent 那侧不做限制，不会阻塞。Agent 侧阻塞的是多个不同主服务同时发指令，它确保一个主服务的指令全部完成后，再执行另一个主服务。

**代码原本没实现这个语义。** 改成：

- 1 个 claim 循环 + N 个执行槽（各自线程）
- `_slot_available(controller)`：**有空槽** 且 **没有别的控制器占着这台机器**
  - 同一主服务：不被自己阻塞（它的任务在它自己那边排队，因为它更清楚为什么要提交这些任务）
  - 不同主服务：必须等前一个**完全做完**
- 槽位在起线程**之前**预占，避免"检查完"到"跑起来"之间超订
- `max_concurrent_tasks` 默认 4，Agent 本地配置

### busy 语义不变

按用户要求，`busy` 保持"这台机器被占着"的原意，**不改**。新增两个字段：

- `waiting_controllers`：前面还有几个**控制器**在排队
- `max_concurrent_tasks`：本机并发上限

用"控制器数量"而不是"剩余槽位"：槽位是本机实现细节，控制器拿到一个自己控制不了的数字没有用。

---

## 52.3 并发数为什么不给模型定

用户问过"能不能让 AI 自己判断并发开到多少"。**不能，这是整个设计里最不该交给模型的一项。**

不是低估模型，是**信息不对称**。模型看得见"有 100 台机器"，看不见：

- 目标机器是 2 核还是 64 核
- 当前负载
- 网络 RTT 和丢包
- 一次要开多少连接
- 主服务自己的连接池上限

**让模型判断并发度，等于让一个看不见现场的人决定开多少台挖掘机。**

更糟的是失败模式：并发过高**不会干净地报错**，会以"超时""连不上"散落在结果里。模型看到 30 条超时，会去排查 30 台并不存在的故障。**这是最坏的一种错误：它让模型自信地诊断错误的东西。**

对应长期原则：**产品约束用软件硬限，不靠提示词自觉。**

模型该能表达的是**优先级**（"这个急""这个不急"），不是**并发度**。

## 52.4 主服务层：扇出工具（已完成）

`read_many(tool, params, asset_ids, run_as)`。模型发一次调用，主服务展开成 N 个只读子任务并发派发，**汇聚一份结果**返回。

落盘：`ai_ops/fanout.py`（纯决策：规划 + 汇聚）、`ai_ops/fanout_runner.py`（调度与完成判定）、`scripts/rehearse_fanout.py`（端到端演练）。

**为什么不用多 tool_call**：多调用会让审批、审计、顺序全面复杂化，并给出 N 条散落 blob；扇出是**一次调用、一份名单快照、一条审计**。

**父任务机制**：扇出创建一个 `kind=fanout` 的父任务 + N 个普通只读子任务。父任务不带 argv、被 claim 查询排除，它存在的唯一意义是让主轮次继续只等**一个** id——这样脱敏、审计、取消、工具输出构造都不需要新增分支。

### 硬约束（均已实现并测试）

| 约束 | 值 | 理由 |
|---|---|---|
| 单次资产数 | ≤ 50，**超了拒而不是截** | 模型以为读了 100 台实际只读 50，会自信地基于半个图景推理 |
| 派发并发 | 10（主服务定） | 连接池是本地的，模型看不见 |
| 总文本预算 | 24000 字符，单台 ≤ 2000 | 40 台 × 5KB = 上下文爆炸，不是结果 |
| 超时预算 | 180 秒 | 一台死机不能把整个扇出拖死 |

### 最重要的一条：结局不合并

`ok` / `unreachable` / `timeout` / `running` / `cancelled` / `unknown` **必须分开**。

理由：如果三台机器都是空输出，一台是“读了但为空”，两台是“连不上”，合并成“无数据”会让模型以为**三个服务都挂了**。答案里明确写 “unreachable 和 timeout 表示数据**没读到**，不要当作服务证据”。

### 父任务的成败语义

父任务在**扇出完成**时报 `succeeded`，不是“每台都成功”。否则一台宕机就把其余 49 台的结果全丢掉，模型对本次故障什么都没学到。

### 顺手修的接缝 bug

claim 查询里“前序任务未完成就不派发”的子句会**让父任务阻塞自己的子任务**（它们同属一轮）。已在 SQL 里排除 `kind=fanout`。

## 52.5 等待原语（已完成）

与并发无关，独立做：

- `start_task(...)` → 返回句柄，立刻返回
- `check_task(handle)` → 立刻返回当前状态
- 用户可随时取消

**不能设计成"sleep N 秒再查"**——那还是阻塞，只是换个说法。

关键：句柄必须绑在**轮次**上，用户点"不等了"，轮次直接往前走，模型拿到"用户放弃等待"而不是超时错误。

### 实现位置

| 件 | 位置 |
|---|---|
| 句柄表、结局、工具描述 | `ai_ops/waiting.py` |
| 工具分派、停放与唤醒 | `ai_ops/turns.py`（`_start_task` / `_check_task` / `advance` 的 `waiting_task` 分支） |
| 停止等待接口 | `POST /api/v1/turns/{id}/stop-waiting` |
| 测试 | `tests/test_waiting.py`、`tests/test_check_task_flow.py` |

### 三种结局，只有一种是"结束"

| 结局 | 含义 | 模型拿到的 |
|---|---|---|
| `finished` | 任务真结束了 | 任务结果本身 |
| `abandoned` | 用户说"不等了" | `still_running: true`，**不是错误** |
| `expired` | 截止时间到了 | 同上，**不是超时失败** |

给模型**绝不给裸的 `timeout`**。裸失败会让它重跑一遍构建或宣布任务坏了——在真机上重跑就是两份构建。

### 停放与唤醒的判定规则（踩过的坑）

1. `waiting_task` 的 transcript **不以"待回答的 tool_call"结尾**——`start_task` 自己就把答案追加了。所以不能用 `waiting_tool` 那套形状判断。
2. 停放后**第一件事是让模型说话**：句柄作为 tool 输出给到模型，它才有机会调 `check_task`。否则句柄永远到不了模型手里，"边跑边干"只是工具描述里的一句空话。
3. 唤醒优先级：**任务结局优先于状态查询**。任务已结束还回"still running"，模型会再等一轮。
4. 事务内的行是快照：`resolve_ready` 改了状态后必须重新 SELECT，否则拿旧行做判断会把已经往前走的轮次又按回去。

### 边界

- 句柄只在本轮有效，跨轮读到 `WAIT_HANDLE_UNKNOWN`。
- `check_task` 立即返回、绝不阻塞。
- 放弃等待**不取消任务**；任务照常在主机上跑。
- 授权不因等待放宽：`start_task` 与 `propose_change` 同一条审批与策略链。
- `readonly` 模式拿不到这两个工具（免得停在写任务上等于提权）。

## 52.6 放开并发时，权限模型要补的

并发一旦放错地方，**最危险的不是崩，是它在特定时序下悄悄给出错误结论**。所以：

| 边界 | 规则 |
|---|---|
| 只读 vs 写 | 只有 `readonly` 参与并发；写、审批类**一律串行** |
| 名单快照 | 并发任务共用**同一份快照**，不各自生成 |
| 审计 | 扇出记**一条**发起记录 + N 条子任务记录，用同一 correlation id |
| 结果过期 | 汇总结果标注每台的**采集时刻**，跨时太久要提示"时间线不对齐" |

最后一条容易被忽略，但在宕机排查里很关键：第 1 台和第 100 台之间隔着几十分钟，**时间线本身就不对齐**，汇总出来的"先后顺序"是假的。
