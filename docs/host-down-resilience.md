# 受控机宕机场景与应对设计（待实现）

状态：设计定稿，2026-10-19。后续实现时以本文为准。
关联：heartbeat-telemetry.md（心跳与指标）、protocol-v11.md、install.sh（systemd 加固）、ROADMAP.md。

## 0. 核心结论

用户原始诉求："在用户服务器上划出一片区域（如 5% CPU/内存），保证执行 Agent 在机器濒死时还能缓一口气传信息。"

结论：**"划区域自保"只对"假死"有效，对"真死"物理上不成立**。正确设计是分层：

1. 假死（资源耗尽，机器还活着）→ cgroup 保护让 Agent 最后倒下，坚持上报关键信号；
2. 真死（内核崩溃/掉电/硬件故障）→ 本机一切用户态进程必死，只能靠**带外通道**（IPMI/BMC/云 API）和**主机侧黑匣子**；
3. 无论哪种死法，服务端都要做到**失联本身就是可用的排查输入**。

按死法分类设计，不承诺"agent 缓一口气救活死机"这种做不到的事。

## 1. 死法分类与覆盖矩阵

| 死法 | 典型表现 | 本机 Agent 能否自保 | 应对层 |
|---|---|---|---|
| 资源耗尽（CPU/内存/IO 打满） | 心跳变慢但仍在，进程活着 | ✅ cgroup 保护后最后一批倒下 | 第 2 节 |
| OOM 全局风暴 | 系统性杀进程 | ✅ 同上，Agent OOMScore 最低 | 第 2 节 |
| 内核 panic | 秒级全死，可能自动重启 | ❌ 用户态必死 | 第 3 节（kdump） |
| 掉电 / 硬件故障 | 毫无征兆全死 | ❌ | 第 4 节（带外通道） |
| 网络分区（机器其实健康） | 双方都活着但失联 | ✅ 本地缓冲 + 重连 | 第 5 节 |

实现第一步只做第 2、5 节（纯软件，零依赖）；第 3 节随 install.sh 收尾；第 4 节是企业版能力。

## 2. 假死自保：Agent 进程保护（开源版，install.sh 随装生效）

### 2.1 systemd 层（Agent 服务单元）

```ini
[Service]
# 内存风暴时 OOM killer 最后才考虑 Agent（-1000 保留给内核，-900 近似最优先保护）
OOMScoreAdjust=-900
# cgroup v2：CPU 权重高于普通负载（默认 100）
CPUWeight=200
IOWeight=200
# 内存下限保护：cgroup v2 memory.min，内核保证不回收（按 Agent 实际常驻 RSS 调整，初始给 64M）
# 通过 unit 内 ExecStartPre 或 drop-in 写入：
#   echo 64M > /sys/fs/cgroup/<slice>/memory.min
```

要点：用**竞争规则保护**（OOMScore + 权重 + memory.min）而非"划死 5%"。划死配额有两个缺陷：平时浪费资源；且内核/其他 cgroup 风暴时不保证兑现。memory.min 是内核契约，比百分比预留可靠。

### 2.2 濒死行为（Agent 内实现）

- 心跳包必须**极轻**（不能依赖采全量指标才上报）；资源紧张时降级为"只发心跳 + 三个数：load1 / mem used% / 最近一次采集"，保证濒死时信号先出去。
- 采集与上报解耦：本地环形缓冲，上报失败落盘（见第 5 节）。

### 2.3 诚实的边界

Agent 活着 ≠ 能干活。濒死场景 Agent 的价值 = 持续传出"我还活着 + 机器指标"，让服务端能下结论"这是资源型濒死，不是网络断了"。诊断和处置由平台侧完成。

## 3. 真死善后：主机侧黑匣子（开源版，install.sh 可选安装）

- **kdump/crashkernel**：内核 panic 时把内存快照落盘 `/var/crash`，重启后 Agent 第一件事检测并回传事件（不上传完整 vmcore，先传 panic 时间、`dmesg` 尾部、vmcore 文件元信息）。
- **journald 持久化**：确保 `Storage=persistent`（install.sh 检查，默认很多发行版是 volatile）。
- **重启后回传**：Agent 启动时检查上次非正常关机标记（`last -x` / `/var/crash` / journal "Previous boot"），生成"宕机事件"上报，作为排查材料。

## 4. 带外通道：真正的死机排查能力（企业版）

机器死透后，唯一还活着的是 BMC 独立芯片。平台对接方式：

- **物理机**：IPMI / Redfish（iDRAC、iLO、Supermicro 等标准接口）。能力：硬件传感器读数、SOL 串口重定向（看死机现场屏幕）、电源操作（强制重启/开关机）。
- **云主机**：云厂商 API 即带外通道（实例串口日志、强制重启、控制台截图）。按 provider 插件接。
- **产品定位**：对接 BMC/云 API 作为新的 connector 类型，复用现有凭证抽象（Credential），读类操作（看传感器/串口/日志）走闸2 白名单，电源操作走闸4 审批——正好是四道闸的直接应用场景。
- 话术对甲方：**带外管理 / 死机取证**，是"机器死了也排查得了"的能力，区别于所有只在 OS 内工作的竞品工具。

## 5. 失联与补偿（开源版，服务端 + Agent 协作）

### 5.1 失联即信号（服务端）

- 记录每个节点的最后心跳时间与**最后 N 条指标**；节点失联时，"失联时间线"自动成为排查材料：
  - 失联前几分钟 load/内存爬升 → 资源型濒死（配合第 2 节 Agent 传出的最后信号佐证）；
  - 失联前毫无征兆、指标正常 → 网络/硬件/掉电型（优先查第 4 节带外通道）。
- 告警规则：心跳超时分级（如 1 个周期 = 提醒，3 个周期 = 失联事件），复用 alarms.md。

### 5.2 Agent 本地黑匣子（Agent 内实现）

- 本地环形缓冲（内存）+ 落盘 spool（如 `/var/lib/<agent>/spool/`，磁盘限额如 50M，超限丢最旧）。
- 缓冲内容：按序号的遥测/事件/执行结果回执。网络恢复或进程重启后按序号补传。
- 与协议的关系：补传即 protocol-v11 的 seq 确认机制的自然延伸——**连接是易失的，数据是非易失的**（与 WebSocket 扩容同一条设计原则）。

## 6. 实现顺序（后续排期）

1. install.sh 加 systemd 加固 drop-in（OOMScore/CPUWeight/memory.min）——半天级。
2. Agent 本地 spool + 重连补传 + 启动时宕机事件检测——依赖 protocol seq，随协议改造一起做。
3. 服务端失联时间线 + 分级告警——随 alarms 改造一起做。
4. kdump 检查与安装引导（install.sh 可选项）。
5. 企业版：BMC/Redfish/云 API connector（独立排期，依赖凭证抽象落地）。

## 7. 对外承诺口径

可以承诺：濒死时可观测、失联有据可查、重启后自动取证、死机可带外排查（企业版）。
不承诺：本机自保能救活已死内核；"预留资源保证永不失联"。
