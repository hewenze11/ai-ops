# AI 运维平台架构评审请求（2026-10-20）

## 评审任务

你是被请来的第三方评审。请以攻击者/架构评审者视角，回答两个问题：

1. **这个产品的架构思路有没有问题？** 包括：设计矛盾、安全模型漏洞、被忽略的边界情况、范式层面的根本缺陷。不要复述优点，直说问题。
2. **落地难度有多大？** 哪些部分容易、哪些部分是深坑、按什么顺序落地最稳。给出你认为的最大落地风险。

要求：观点鲜明，基于工程现实，不要客套和免责声明。可以用编号列出问题并标注严重度（🔴致命/🟠严重/🟡中等/🔵建议）。

## 产品概述

一个 AI 运维平台：用户把服务器作为资产接入（本地 connector 或 SSH/自部署 Agent），通过对话让 AI 排障、巡检、执行变更。核心范式：

> **AI 全权调查（读），人类独占变更（写）。**

定位：对标"OpenClaw 定义了 AI 操作个人电脑的范式"，我们定义"AI 操作生产服务器的范式"。开源 + 商业化（Skills 订阅/领域包/企业版）。

## 核心架构设计（均已定稿，设计文档在 projects/ai-ops/docs/）

### 1. 权限模型：四道闸（readonly-and-authorization.md §39 已修正）

- **闸1 工具级**：readonly 模式下模型根本拿不到 execute_command 工具（非提示词约束）。
- **闸2 只读通道**：白名单 + argv 直 execve（不经 shell，`|`/`$()`/重定向无载体）。校验在最终执行端点（Agent/connector）独立再做一次；白名单永不收录解释器类程序；白名单故意窄（宁拒绝合法、不放行危险），缺口走闸4。
- **闸3 结构化写通道**：不审查自由 shell（原理上不可行），而是平台预定义动作表（目标定位方式限定、参数约束、禁自由 shell 逃逸），AI 只能选动作+填参数。官方默认包 + 用户自定义（带责任标记）+ 可售卖的变更策略包。
- **闸4 人工审批**：每条写操作绑定不可变执行载荷哈希（资产+身份+完整 argv），执行前重新校验，防"批 A 执行 B"。生产资产有摩擦设计。
- **凭证抽象**：目标机账号/云账号统一为 Credential，密文 AI 不可见；默认全无、用户显式开。
- **兜底**：目标机 sudoers 只读账号（Cmnd_Alias 白名单，install.sh 自动建）。

### 2. 机械验证（针对"模型未经验证的完成声明"）

- 闸3 每个动作绑定平台预定义的后置校验（postcondition），由平台代码执行、平台代码出结论（布尔+原始输出），不走模型。
- 审计记录存命令/退出码/原始输出，模型的事后总结只是附注。
- 信任接口收窄到"模型填参数"，不要求任何模型"诚实"。

### 3. 平台自指边界（readonly-and-authorization.md §40）

- AI 可看/分析平台、可对平台配置出 diff 提案，但**不能改平台的任何东西**（守门人不能被被守的东西修改）。
- 平台宿主机作为特殊自纳入 connector 接入，锁 readonly-observer 档。
- 审计完整性三层：connector 独立 OS 账号与服务账号分家（配置 600）；审计表 DB 角色仅 INSERT/SELECT（追加即定稿）；异机存证（企业版审计外送）。

### 4. 模型与执行者治理

- 审计记录每轮实际使用的模型；写通道任务可配置模型下限，低档模型拒绝接单。
- 起因：真实事故——某厂商静默把任务从强模型路由到 flash 级模型，导致部署配置错误 + 生产事故。

### 5. Tools 层（tools-and-websearch.md）

- 新增：search/fetch（一个工具 + Provider 抽象：默认 DuckDuckGo 免费，可选 SearXNG/Brave/Tavily 用户自配 key）；日志/指标专用只读查询工具。
- 强制脱敏（query 中主机名/IP/内网域名平台层改写）；外部内容按不可信文本处理（防 prompt injection），由此产生的动作照走四道闸。
- 明确不加：浏览器自动化、消息群发、带凭据的通用 API 调用、独立定时任务。

### 6. Agent 拓扑与协议

- 主服务（单信任域，多用户同权限起步）+ 每资产一个自部署执行 Agent（长连接，断线重连 + 消息 seq 补偿，本地 spool 落盘）。
- Agent→主服务认证：一次性 agent_token 认主；计划加主服务身份证书 pinning（防中间人）。
- 技术栈：Python/FastAPI，SQLite（企业版换 PG），Docker/脚本双部署。

### 7. 宕机与可靠性（host-down-resilience.md）

- 假死：cgroup 保护（OOMScoreAdjust=-900、CPUWeight、memory.min），不用死配额。
- 真死：kdump 黑匣子 + 重启后自动取证；企业版 IPMI/Redfish/云 API 带外 connector（读走闸2、电源操作走闸4）。
- 失联时间线即排查输入；Agent 本地缓冲按 seq 补传。

### 8. Skills 体系（产品层）

- Skill = 纯知识/方法论（"结构设计式"任务书：目标+验收标准+约束红线+现场检查点+方法论与坑+升级条件），平台无关 Markdown，可移植，兼容 SKILL.md 生态。
- 明确拒绝"傻瓜式步骤文档"（环境差异下死步骤必劈叉，且给模型免责错觉）。
- Skill 文本按外部注入文本对待（与网页同级不可信），无权自我授权；引用 Skill 的操作审批时标注来源；官方/第三方包打标。
- 知识层搬运现成沉淀（awesome-prometheus-alerts、Ansible roles、SRE runbooks），逐仓核 license；平台留导入功能。

### 9. 商业模型

- 开源（AGPL-3.0 本体）+ Skills 订阅（官网账号签发订阅 API Key，自部署主服务拉取，模型 key 用户自配）。
- 三档：基础订阅（通用运维 Skills）/ 领域包（按价值定价：等保三级合规包第一个，安全审计包第二）/ 企业版（私有部署、PG、带外管理、审计外送）。
- 课程：一次性终身会员，定价区间 [500, 2000+] 由开源后市场热度决定。

## 追求的目标

1. 短期：单人可稳定管理 ~50 台服务器，开源后获得真实用户与市场信号。
2. 中期：Skills/领域包商业闭环，等保合规场景落地。
3. 长期：定义"AI 操作生产环境"的范式（AI 调查自由 + 人类独占变更），成为该品类的事实标准。
