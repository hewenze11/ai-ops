# 资产生命周期与失联事件

## 1. 删除一台机器：注销 vs 彻底删除

过去"删除资产"是一个含混的动作。运维真正想表达的其实是两件**完全不同**的事：

| 动作 | 语义 | 历史 | 可恢复 | 默认 |
|---|---|---|---|---|
| **注销（retire）** | 这台机器不再由我管了 | **保留** | ✅ 可恢复 | **是** |
| **彻底删除（purge）** | 记录必须消失 | **一并清除** | ❌ 不可恢复 | 需显式确认 |

**原则：历史就是证据。** 一台主机上跑过的任务、写下的审计，是"发生过的事实"。
因此：

- **注销**只是给资产打上 `retired_at`，把它从**资产列表**隐藏，一切历史原样保留，
  随时可恢复（`unretire`）。
- **彻底删除**是会真的删数据的破坏性操作，必须**回显资产 ID 作为确认**，且在
  该资产还有**未决执行**（`claimed` / `unknown`）时**一律拒绝**——那正是运维可能
  最需要的证据。先 `resolve`/`abandon` 再删。

### API

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/assets/{id}/retire` | 注销（body: `{note}`） |
| POST | `/api/v1/assets/{id}/unretire` | 取消注销 |
| POST | `/api/v1/assets/{id}/purge` | 彻底删除（body: `{confirm_asset_id}` 必须等于路径 id） |
| GET | `/api/v1/assets/{id}/lifecycle` | 生命周期 + 失联事件 |

`purge` 会在**同一个事务**里按外键顺序清理依赖行（输出分块/归档、任务控制、租约、
任务本身、agent 在线记录、连接信息、本地纳管标记），要么全删、要么全不删。

## 2. 机器失联（不是注销）

机器**失联**是"它还在，只是不吭声了"，与"注销"是两回事。

**边界（重要）：**

> **检测失联是平台的职责；是否通知、通知给谁，交给已经配置的告警 Webhook。**
> 平台**不**自己去探测主机，也**不**自动重派它上面的任务（见 docs/leases.md）。

流程：

1. 平台发现某资产的 agent 心跳**超过在线阈值 30 秒**（与执行模块一致）。
2. 但**不是一到 30 秒就报**：还须**连续静默超过 90 秒**（防抖，等价于
   Alertmanager 的 `for`），避免一次网络抖动就惊动人。
3. 满足后生成一条**持久化失联事件**；同一资产在 1800 秒内**最多再报一次**，
   防止刷屏。
4. 若已配置告警 Webhook，事件会**排入同一个出站队列**（复用告警外推的通道），
   在消息里推一条 `[资产失联] <名称>`。**没配置就只留事件**（控制台可见），不报错。
5. 主机**恢复心跳**后，清空该资产的防抖计数，只有它**再次静默**才会重新报警。

### 为什么用同一个 Webhook

失联通知**不是**第二套监控系统。它复用告警外推的**那一个** URL：
Alertmanager 仍是第一棒，平台只是把一个信号交给它、由用户决定要不要落成通知。

### API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/assets/offline` | 当前静默资产（实时视图，无副作用） |

## 3. 开关

- `AI_OPS_OFFLINE_WATCH_ENABLED=0`：关闭失联检测后台线程（默认 `1`）。

## 4. 控制台

"资产与知识 → 资产生命周期"页签：展示当前失联资产、按 ID 查询某资产的生命周期与
失联事件、对已注销资产一键恢复。资产编辑弹窗内提供"注销"与"彻底删除"两个动作，
后者需输入资产 ID 确认。

## 5. 测试

`tests/test_asset_lifecycle.py`（12 项）：注销隐藏但保历史、恢复、彻底删除需确认、
彻底删除清理依赖行、未决执行时拒删、失联检测生成事件、防抖不刷屏、短抖不动、
恢复后重置防抖、失联事件推入 Webhook、无配置时不报错、已注销资产不计失联。
