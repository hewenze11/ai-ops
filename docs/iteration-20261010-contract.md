## Scope and authority
- New execution_grants is an array of `{asset_id, username}`. Identity is the stable asset ID plus exact registered OS username; asset display names are not identity. Account notes are descriptive only. Same-asset duplicate usernames rejected; cross-asset names allowed.
- Stage-one implemented compatibility: direct task API scopes execution_users to its explicit asset_id. At an authenticated NEW chat/custom-task/pairing submission only, legacy names are narrowed ONCE to the unique currently registered asset for each username; ambiguous same-name accounts return 422, unmatched names grant nothing, and chat/custom-task responses include a deprecation warning. The resulting asset+username snapshot never expands after later registration. New console uses execution_grants. Existing persisted histories/legacy queued authority are never resolved by matching names; unscoped dispatch fails closed. This replaces the earlier draft's stricter legacy-input rejection without weakening asset isolation. Pairing warning UX and full migration guidance still need review.
- Grants are checked at enqueue, tool execution, task creation, claim and connector dispatch. Asset/Agent allowlists and OS capability boundaries remain mandatory. Registration is not authorization.
- Dedicated request_execution_account tool accepts asset_id, username, reason; returns persisted waiting_user authorization request. POST /api/v1/turns/{turn_id}/account-requests/{request_id}/answer accepts approve/reject with revision. Only administrative HTTP authority can approve; ask_user answers never authorize. Approval adds one grant only to this turn. Missing account cannot be approved until registered independently. Cancel/terminal cancels pending requests. Preserve initial grants, append authorization events and per-command grant revision. Actor is shared admin-token trust domain, not verified human identity.
