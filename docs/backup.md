# 备份与恢复

业务状态在 SQLite 数据库里（roles、assets、tasks、audit、输出、leases、turns、documents、定制任务）。2026-10-09起角色独立模型Key在受控文件目录，数据库仅存不可变引用，不存明文。

**数据库快照另带角色密钥目录**：例如 `manual.db`、`manual.db.meta.json`、`manual.db.role-secrets/` 必须一起保管/迁移，目录0700、Key文件0600。只复制快照所引用的角色凭据，不把Key写入数据库/JSON/API响应。校验拒绝缺少凭据旁车的快照，恢复先安装缺失的不可变凭据修订、再切数据库；现有同名修订内容冲突时拒绝。角色密钥旁车是敏感备份，需受控保存，勿公开上传。

admin token、全局model key与**旧式外部文件引用的SSH凭据**不进入这个数据库快照命令；部署级完整备份需另行保存。通过 `ssh_secret` 提交的**托管SSH密码/私钥**则按下面的规则备份，不能与旧式文件引用混淆。默认角色密钥目录为DB父目录的 `role-secrets`；使用 `AI_OPS_ROLE_SECRET_DIR` 自定义路径时，备份/恢复进程也必须带同一目录设置。

## 托管SSH凭据与图片附件（2026-10-10）

存在相应数据时，迁移快照必须同时保留：

- `manual.db.connector-secrets/`：该快照引用的SSH凭据密文。
- `manual.db.connector-keys/`：上述密文所需的密钥旁车；**与密文一起取得即可解密**，因此整个备份仍属于敏感数据，不是无密钥的加密归档。
- `manual.db.attachments/`：快照所引用的图片文件。
- 前述 `manual.db.role-secrets/` 与 `manual.db.meta.json`。

SSH密文或密钥缺失、损坏时，备份不能报告成功，校验/恢复也会拒绝。校验依赖数据库中的实际引用，不依赖元数据声称的数量；数据库旧版、没有托管SSH引用时不要求SSH旁车目录。元数据仅记录托管凭据数量，不包含秘密。

恢复会使用**目标机器的主密钥重新加密**，只改写暂存数据库中的SSH文件引用，不使用原机器的绝对路径，也不覆盖目标已有密钥和旧凭据。目标没有密钥且没有既有密文时可创建新密钥；已有密文却缺主密钥时拒绝恢复，禁止悄悄换密钥导致旧凭据失效。

默认目录为DB父目录的 `connector-secrets/`（密文）与 `connector-keys/master.key`（主密钥）；可用 `AI_OPS_CONNECTOR_SECRET_DIR` 和 `AI_OPS_CONNECTOR_MASTER_KEY_FILE` 指定。备份应使用源服务的设置，恢复使用目标服务的设置。目录0700、文件0600适用于POSIX；Windows需另外配置账号访问控制。数据库、安全副本和所有凭据旁车均需管理员级保护。

## 快照是怎么做的

- 用 SQLite 的**在线备份 API**（`Connection.backup`），在 WAL 模式下**不停服务、不打断写入**也能得到事务一致的快照，绝不会看到写了一半的事务。
- 先写到 `.partial` 临时文件，`fsync` 落盘后再原子改名，避免"崩溃后留下一个自称完整其实不完整的快照"。
- 生成后立刻做 `PRAGMA integrity_check` 与 schema 版本检查，通过才写同目录的 `.meta.json` 边车（含 schema 版本、大小、sha256、主要表行数、创建时间）。
- 文件权限 0600。

## 校验

`inspect` 以 `mode=ro` **只读**打开候选库，任何校验都不会改动文件。它检查：文件存在、是可读 SQLite、`integrity_check == ok`、schema 版本在支持范围内（高于本版本构建的拒绝），并统计主要表行数。

`verify_backup` 在 `inspect` 之上核对已有元数据边车：sha256 必须与数据库一致、schema一致，并确认角色密钥、图片附件及托管SSH密文/密钥完整；托管SSH凭据还须通过解密校验。不会把凭据内容返回给调用者。任一处不符即判定备份不可用。凭据备份目录仍须由主机/备份访问控制保护，本功能不是整个备份的加密服务。

## 恢复

`restore_backup` 的顺序是关键：

1. 先**完整校验**候选备份——校验不过就地失败，**绝不碰生产库**。
2. 安装角色凭据和图片附件，把校验过的数据库复制到 `.restore-incoming`；重新加密托管SSH凭据并改写暂存引用，回写暂存库WAL、fsync后**再次校验**。
3. **先把生产库的 WAL 回写（checkpoint）进主文件**，再把当前生产库**原子改名**为 `control.db.pre-restore-<时间戳>-<随机后缀>`（保留回退路径）。WAL 模式下最近的提交在 `-wal` 文件里，若只改名主文件会把它们悄悄丢掉、留下一个不可用的回退副本。
4. 删除旧的 `-wal` / `-shm`，避免陈旧 WAL 被回放到恢复后的文件上。
5. 原子改名把恢复副本装到位，并确认不残留 `.restore-incoming` 临时文件。

切换数据库失败时会尝试把旧数据库移回原位，并清理本次重新加密产生的新凭据及暂存数据库。若底层文件系统连回滚也失败，则明确报错、保留 `.pre-restore` 副本供人工恢复；不能宣称任意故障下均自动恢复。已有凭据不删除，新复制的角色凭据/图片可能保留为未引用文件。本流程也不宣称断电级跨文件事务原子性。

> 恢复**必须先停止服务**，成功后再启动：运行中的进程仍持有旧数据库文件的句柄，改名后它不会自动切到恢复后的文件。CLI本身不负责停服务。

## 操作方式

命令行（在容器内或持有挂载目录的宿主机上）：

- `ai-ops-backup --out /data/backups/manual.db`：写一个快照。
- `ai-ops-verify-backup /data/backups/manual.db`：只校验，不恢复。
- `ai-ops-restore --from /data/backups/manual.db [--check]`：校验并恢复；`--check` 只校验。

数据库路径默认取 `AI_OPS_DB`。

管理员接口（只做快照，**恢复刻意只走 CLI**）：

- `POST /api/v1/backup`：在 `<数据库目录>/backups/` 下写一个带时间戳的快照，并写审计。
- `GET /api/v1/backup`：列出已有快照及其元数据。

为什么恢复不提供 HTTP 接口：一次已认证的调用就能覆盖生产状态、且无法在接口层确认目标路径，风险不对称。恢复设计为运维人员在宿主机上的显式动作。

## 不宣称的

- 不提供自动定时备份。快照需要运维人员触发（可在宿主机加 cron）。
- 不提供异地/对象存储上传；只在本机磁盘上生成文件。
- 恢复不做跨 schema 迁移：高于本版本支持的备份会被拒绝，需要对应版本的服务来恢复。
