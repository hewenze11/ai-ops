# 外部评审报告二：Claude Fable（2026-10-20）

评审对象：external-review-brief.md 及配套设计文档。来源：第三方模型评审（Claude Fable 5.1），原文完整存档。

## 总判断

范式方向对，设计文档自我修正能力高于同类项目（§39 闸3 转向结构化动作表是正确的大转弯）。三个结构性问题：

1. 安全模型核心承诺（读写分离）在"读"侧有一个被低估的大洞：读通道无审批无人票，而读通道本身就是攻击者的全部所需。
2. "人类独占变更"对 50 台成立、对规模化不成立，文档没有正视。
3. 设计文档厚度与实现薄度差约 18 个月单人工作量，而设计文档还在膨胀。

## 架构问题

### 🔴 1. 只读通道零摩擦，但"只读"在生产机上就是最大攻击面
读能拿到：/etc/nginx/*（上游/拓扑/明文密码）、/proc/*/environ 与 cmdline（几乎所有 DB 密码/API key/JWT）、journalctl 与 /var/log/*（token/session/PII）、kubectl get secret -o yaml（全集群凭据）、docker inspect（容器环境变量）、ps/ss/lsof（攻击面地图）。
攻击链：prompt injection（告警内容/日志/网页）→ 白名单工具读 secret → 编进 search query 或 fetch URL → 出站。脱敏抓不到 base64 密码、PEM 中段。完全不碰四道闸（四道闸全是防写的）。**改配置可回滚，泄密不可回滚——这比写漏洞严重一个量级。**
修正：只读白名单加敏感路径黑名单第二层（/proc/*/environ、*/secret*、*.pem、*.key、kubectl get secret、docker inspect Env——此处黑名单是对的，失效方向是拒绝读合法文件）；search/fetch 单独"外联档"需开启，或 query 人工可见（审批卡片显示全文）；读通道改"不阻塞但可见"，流式显示 AI 读了什么。

### 🔴 2. sudoers 与白名单职责重叠，文件级访问控制缺失
sudoers Cmnd_Alias 限制执行哪些程序，不限制程序读哪些文件：cat 在白名单内，sudoers 允许，则 cat /etc/shadow 内核放行。当前"兜底"与软件层白名单同维度重复，无纵深。真正第二维度是 DAC/MAC（只读账号对敏感目录无读权、或 AppArmor）。
细节：read_only 账号读不了 /var/log/nginx（640 root:adm），install.sh 要么加 adm 组（能读 auth.log 等），要么 Agent 以 root 跑再 setuid——root Agent 是整个目标机最有价值的攻击目标，而 Agent 自身硬化（seccomp、capabilities 降权、NoNewPrivileges）几乎没谈。

### 🔴 3. 闸3 动作表：动作抽象层级上，参数就是逃逸面
edit_config_file 的 content 写 include /tmp/evil.conf 或 lua_code_block = RCE（要防需解析 nginx 语法）；patch Deployment 的 command/hostPath = 集群逃逸；systemctl restart sshd 在 sshd_config 被改后锁死全部运维；exec_in_container 根本不该存在但用户肯定要。
结论：每个动作都是需独立安全评审的微型 DSL，官方前 20 个动作每个半天到两天。用户自定义动作本质是把 shell 模板参数化，对任意 shell 模板做禁逃逸校验正是 §39.1 承认不可行的事——设计绕回起点。修正：用户自定义动作一律强制闸4 逐条、不进 auto-approve。

### 🟠 4. 四道闸全跑在同一信任域内，单令牌
审批队列/载荷哈希/动作表定义都在同一 SQLite、同一进程同一权限。攻击者拿到令牌（或 XSS 后台）→ 四道闸全失效；闸4 的"人工一票"只是 DB 一个 status 字段，凡能改该字段的路径都是绕过路径。§40.3 给审计表做了角色拆分，但审批表/动作表/白名单更关键（审计是事后，审批是事中），未获同等保护。
修正：审批决策需要不在主服务进程内的根——最低成本是审批者浏览器端签名（WebAuthn/passkey 签载荷哈希），服务端只验签。半周工作量，需协议层预留。

### 🟠 5. 多控制器与单信任域组合在 v1 就是漏洞
Agent 信任 A、B 两主服务，B 被攻破或被误加仿冒 → 可下发任务；Agent 侧校验不区分任务来自哪个控制器。v1 应配置层硬禁多控制器（只允许 1 个），"代码已支持、治理未设计"就是攻击面。

### 🟠 6. "人类独占变更"在告警场景自我矛盾（范式与市场张力）
告警响应 4-5x 的卖点主要发生在诊断阶段；凌晨 3 点 OOM 告警，AI 诊断完等人批，人在睡觉。SME 用两周必说"让它直接修"→ 打开 auto-approve。而 §39.1 禁止告警/webhook 触发 direct 模式（防注入）→ 告警驱动的自动修复在设计上不存在。
修正：要么诚实定位"AI 诊断+人工执行"；要么设计受限自动化通道：告警驱动 → 动作表 → 预授权策略（仅重启白名单服务、仅非生产标签、每小时 N 次）→ 自动执行 → 事后通知。后者在既有框架内，是 SME 真正买的东西。

### 🟠 7. 载荷哈希解决"批 A 执行 B"，没解决"批时看到的 A ≠ 实际的 A"
审批卡片的人话解释由执行任务的模型生成，而人看的是人话。edit_config_file 600 行 diff 里第 412 行多了 include，审批人不会逐行读。闸4 实际强度=审批人阅读能力×耐心。
修正：审批摘要不能由执行任务的模型生成——由平台代码从结构化参数机械生成（修改文件 X、diff N 行、涉及指令：include/worker_connections），或独立无上下文审核模型生成。分权原则在 AI 内部的应用。

### 🟡 8. Postcondition 覆盖率
不到 30% 运维变更有可机械判定的 postcondition；剩余的退化成"退出码 0"（无意义）或回到模型判断。应标注强/弱 postcondition 等级并在审批卡片展示。

### 🟡 9. 宿主机自纳入 connector：隔离变成同机不同账号
平台进程 /proc/*/cmdline 全用户可读——若 secret 被作为命令行参数传（--database-url postgresql://...）就泄了；还有 ss -p、/proc/*/fd。且"看平台健康"价值低（/healthz 已有）、风险高，为统一性付出不对称代价。建议 v1 不做自纳入。

### 🟡 10. Skills 不可信但指导写操作，信任传递未闭环
恶意/被污染 Skill 可让 AI 产出看起来专业的变更计划，人看计划觉得专业就批了。修正：Skill 信任等级直接影响该轮可用动作集合与审批策略——引用第三方 Skill 的轮次，auto-approve 强制关闭。

### 🟡 11. Agent spool 落盘=敏感数据汇编
spool 存执行结果回执=cat 配置输出=kubectl get secret 输出，50M 明文在目标机。目标机被入侵即多拿一份"AI 最近读过的敏感内容汇编"。需加密（密钥主服务下发仅内存持有）或只 spool 元数据。

### 🔵 12. 其他
- 证书 pinning 一天工作量，不要排"计划"，部署第一天就要。
- 告警 webhook 是最直接的 prompt injection 入口（攻击者只需在某被监控应用 URL 塞 payload 触发告警），防护重心不应只放 web 抓取。
- SQLite 并发审批竞态（两人同时批、批与撤销并发）未提。
- 模型下限依赖厂商返回名（起因事故即静默路由），应记录响应 header 实际模型+定期探针检测能力漂移。

## 落地难度

### 容易（2-4 周）
闸2 核心逻辑约 200 行（难在白名单终稿与参数约束测试，15 命令起步）；证书 pinning 1-2 天；TLS 用 Caddy 不要自写 ACME；systemd 加固半天；审计 DB 角色拆分仅 PG 可行（SQLite 硬限制）；search/fetch 脱敏易写难写对。

### 深坑（各为月级）
1. 闸3 参数约束：不是代码坑是安全设计坑，AI 会给出看起来完整实际有洞的约束；前 20 动作 3-4 周全职+外部安全评审。
2. root Agent 自身硬化：seccomp/capabilities，系统编程级知识，2 周+持续。
3. 审批 UX 与 yes 工程师对抗：产品坑，需真实用户迭代。
4. SQLite→PG 并发层重做（2-3x 估算）；且审计/审批保护依赖 PG → PG 不是企业版可选而是安全模型前提 → 开源版安全承诺比企业版弱一档，须诚实写出。
5. 误拒率运营张力：白名单宁拒绝 → AI 频繁被拒 → 绕路 → 误拒率高 → 用户要求放开 → 白名单膨胀。无一次性解法，需从第一天埋点拒绝率。

### 最稳落地顺序（对现有 §10 两处调整）
```
第 0 步（1 周，先于一切）：TLS 默认开（Caddy）+ 管理面默认绑 127.0.0.1 + 证书 pinning；
  多控制器配置层禁用；告警 webhook 内容进 AI 上下文加 [UNTRUSTED ALERT PAYLOAD] 标记。
  ——这些是"现在就在裸奔"的项目，不做完不该让外人部署。
第 1 步（2-3 周）：闸2 只读通道，15 命令起步+敏感路径黑名单，默认不含 search/fetch。
第 2 步（1 周）：只读账号+sudoers+敏感目录 DAC 检查。
第 3 步（2 周）：闸4 增强先于闸3：载荷哈希、机械生成审批摘要、审批与 Skill 来源/模型等级联动。
  ——闸4 是当前唯一真实写保护，闸3 落地前必须够硬，且可独立交付。
第 4 步（4-6 周）：闸3 动作表，官方 10 个起步（不要 20），带 postcondition 等级；自定义动作 v1 不做或强制闸4 逐条；外部安全评审一次。
第 5 步：search/fetch（外联档+query 可见）。
第 6 步：受限自动化通道（SME 真正付费点），须在闸3 稳定后。
第 7 步：宕机/spool/联邦/自纳入全部后移，v1 不做。
```

### 最大落地风险
1. （最大）设计膨胀速度 > 实现速度且方向分叉：设计在想第 9 层，实现卡在第 1 层，每次讨论往第 10 层加东西。现有 sh -c 路径已在公网预览上线，四道闸一道都不存在——若开源时安全叙事与实现不符，第一个认真看代码的人会把它钉在耻辱柱上，对以安全范式为卖点的产品是声誉级致命伤。建议：冻结设计文档至少 8 周；README 安全声明逐条对应有测试覆盖的代码，否则不写。
2. 单人+AI 写安全关键代码无独立评审：正确性=安全性的代码，一个 off-by-one 就是 RCE。闸2/闸3 核心校验发布前需一次外部人工审查（不是模型审查）。
3. 范式与市场张力被回避 → SME 用户用 direct+自定义动作+auto-approve 自己拼后门 → 事故 → 归咎产品。必须主动给出"安全的自动化"路径。

## 一句话总结

安全叙事比安全实现超前约一年，且叙事本身在"读"侧有可被 prompt injection 直接利用的外传漏洞。先一周堵裸奔项、把 search/fetch 从只读档拆出去、冻结设计、把闸2+闸4 做硬并经外部审查后再谈开源发布——否则"定义 AI 操作生产服务器的范式"这句话会被第一个认真读代码的人反过来定义。
