# §52 并发与等待（2026-10-23）

用户提出的两个场景：

1. **批量排查**：一台主服务控制 100 台机器，整体宕机时要逐台上去看。要求同时调工具、一起取数、汇总处理。
2. **并行等待**：大任务里嵌套一个十几分钟的构建，其余工作照常推进；要轮询工具；要能"等"或"不等了直接返回"。

下面把"现在为什么不行""怎么改""哪些边界不能动"讲清楚。

---

## 52.1 现状：三重串行

| 层 | 位置 | 限制 |
|---|---|---|
| 模型层 | `turns.py` | `if len(calls) != 1: raise` —— 一次只能发一个工具调用，多发判失败 |
| Agent 层 | `agent.py` | `while True: worker.once()` —— 同步执行到底，执行期间不 claim |
| 轮次层 | `app.py` claim SQL | 同轮次内前序任务未完成，后续任务不派发 |

三层任意一层都会让并行失效。

**Agent 层已经改（§52.2）。另外两层待改（§52.4、§52.5）。**

---

## 52.2 Agent 层：已完成

用户原话的设计：

> 同一个主服务发出去的命令，在执行 Agent 那侧不做限制，不会阻塞。Agent 侧阻塞的是多个不同主服务同时发指令，它确保一个主服务的指令全部完成后，再执行另一个主服务。

**代码原本没实现这个语义。** 改成：

- 1 个 claim 循环 + N 个执行槽（各自线程）
- `_slot_available(controller)`：**有空槽** 且 **没有别的控制器占着这台机器**
  - 同一主服务：不被自己阻塞（它的任务在它自己那边排队，因为它更清楚为什么要提交这些任务）
  - 不同主服务：必须等前一个**完全做完**
- 槽位在起线程**之前**预占，避免"检查完"到"跑起来"之间超订
- `max_concurrent_tasks` 默认 4，Agent 本地配置

### busy 语义不变

按用户要求，`busy` 保持"这台机器被占着"的原意，**不改**。新增两个字段：

- `waiting_controllers`：前面还有几个**控制器**在排队
- `max_concurrent_tasks`：本机并发上限

用"控制器数量"而不是"剩余槽位"：槽位是本机实现细节，控制器拿到一个自己控制不了的数字没有用。

---

## 52.3 并发数为什么不给模型定

用户问过"能不能让 AI 自己判断并发开到多少"。**不能，这是整个设计里最不该交给模型的一项。**

不是低估模型，是**信息不对称**。模型看得见"有 100 台机器"，看不见：

- 目标机器是 2 核还是 64 核
- 当前负载
- 网络 RTT 和丢包
- 一次要开多少连接
- 主服务自己的连接池上限

**让模型判断并发度，等于让一个看不见现场的人决定开多少台挖掘机。**

更糟的是失败模式：并发过高**不会干净地报错**，会以"超时""连不上"散落在结果里。模型看到 30 条超时，会去排查 30 台并不存在的故障。**这是最坏的一种错误：它让模型自信地诊断错误的东西。**

对应长期原则：**产品约束用软件硬限，不靠提示词自觉。**

模型该能表达的是**优先级**（"这个急""这个不急"），不是**并发度**。

---

## 52.4 主服务层：扇出工具（待做）

不要放开多 tool_call，改用**一次调用的扇出**：

```
read_many(asset_ids=[...], tool="journal_logs", params={...})
```

主服务展开成 N 个子任务、并发派发、**汇聚一份结果**返回。

为什么比放开多 tool_call 好：

- 模型仍只发一次调用，绕开 `len(calls) != 1`
- 名额由**主服务**控制（它知道连接池上限）
- 结果**汇聚**成"100 台的对齐视图"，而不是 100 条散落信息
- **权限模型不用动**：一次调用、一份名单快照、一个审计条目

### 硬约束

- **单次上限 50 台**，超过分批。理由：100 台日志各 2KB 就是 200KB，模型上下文会爆。
- **必须汇聚，不能透传**。透传等于把上下文压力转移给模型。
- **超时要单独归类**。不能把"没连上"和"读到了空"混在一起——否则模型会误判。
- **只读可用，写不可用**。扇出只对 `readonly` kind 开放。

## 52.5 等待原语（待做）

与并发无关，独立做：

- `start_task(...)` → 返回句柄，立刻返回
- `check_task(handle)` → 立刻返回当前状态
- 用户可随时取消

**不能设计成"sleep N 秒再查"**——那还是阻塞，只是换个说法。

关键：句柄必须绑在**轮次**上，用户点"不等了"，轮次直接往前走，模型拿到"用户放弃等待"而不是超时错误。

---

## 52.6 放开并发时，权限模型要补的

并发一旦放错地方，**最危险的不是崩，是它在特定时序下悄悄给出错误结论**。所以：

| 边界 | 规则 |
|---|---|
| 只读 vs 写 | 只有 `readonly` 参与并发；写、审批类**一律串行** |
| 名单快照 | 并发任务共用**同一份快照**，不各自生成 |
| 审计 | 扇出记**一条**发起记录 + N 条子任务记录，用同一 correlation id |
| 结果过期 | 汇总结果标注每台的**采集时刻**，跨时太久要提示"时间线不对齐" |

最后一条容易被忽略，但在宕机排查里很关键：第 1 台和第 100 台之间隔着几十分钟，**时间线本身就不对齐**，汇总出来的"先后顺序"是假的。
