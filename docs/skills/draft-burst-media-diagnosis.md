# Skill 草案：`burst-media-diagnosis`（突发媒体业务诊断）

> 状态：**草案 / 待真机实测校准**。作者要求：先用真实生产案例跑通、验证结论准确，再固化入库。
> 归属：`ai-ops` 主服务的 Skills 库（形状 `{id, name, content, role_ids, enabled}`）。
> 可信度声明：本 Skill 的输出分为「实测事实」与「推断结论」两类，推断必须标注依据与置信度。

---

## 0. 这个 Skill 解决什么问题

**现象**：多节点集群（例：4 节点，每节点 8C16G）平时资源宽松，但**偶尔某个单节点的 pod 被 CPU/内存打满，其余节点却很闲**。典型出现在视频 / 图片 / AI 推理这类"重请求"业务上。

**用户最想要的答案**（用大白话）：为什么只有这一台被打满？是不是要去骂开发改代码？该加机器还是该改配置？

**Skill 目标**：给出可落地、分层（代码/配置/架构）的诊断与处置建议，并明确哪些是实测、哪些是推断。

---

## 1. 适用范围与前置条件

- **适用**：容器化（k8s / docker compose）、多副本、有负载均衡入口的在线服务；尤其是单请求资源占用方差极大的业务（媒体转码、大模型推理、图像处理、大文件解析）。
- **不适用**：单实例服务（无从谈"分布不均"）；纯静态资源服务；无法采集到任何 pod/节点指标的封闭环境。
- **前置条件**：能读取到——每个副本的请求量/连接数、CPU、内存（RSS）、OOM 记录、重启次数；入口负载均衡的算法与会话保持设置。**采集不到这些，本 Skill 只能给方向性假设，且必须降级标注为"未验证"。**

---

## 2. 判定模型：先分清"不均"的三种根因

诊断的核心，是判断"单节点打满"到底是下面哪一种（可并存）：

| 根因 | 特征（实测表现） | 大白话解释 |
|---|---|---|
| **A. 请求分布不均（会话粘性）** | 某副本连接数/请求数**远高于**其他；与该副本被分配的"用户/会话"数一致 | 负载均衡把同一用户的所有请求都发给同一台（要"保持会话"），这个用户又特别能发 |
| **B. 单请求过重（重活集中）** | 各副本**请求数相近**，但某副本**CPU/内存远高**；内存呈**锯齿状尖峰** | 每台都在干活，但这台恰好接到几个"巨型请求"（大视频），一个就顶几百个 |
| **C. 入口限流缺失（无节流）** | 总资源占用随时间**单调上升无回落**；单用户可无限并发 | 没有"单用户最多同时发几个请求"的闸门，一个人能把整台机器占死 |

**判定方法**：把「各副本请求数」和「各副本资源占用」两条线放一起看。
- 请求数悬殊 → 偏 **A**
- 请求数接近、资源悬殊 → 偏 **B**
- 总量无节制增长、无回落 → 偏 **C**

> 三者常同时出现：一个能发海量视频的用户，被粘到某一台（A），发的又都是重请求（B），且无单用户限流（C）。

---

## 3. 标准处置建议（分层，务必分开讲）

**不要只回答"叫开发改代码"**，要分三层给，让用户按成本选择：

### 第一层 · 配置层（当天可做，成本最低）
- 把**负载均衡算法**从默认/会话保持，改为**按"当前负载权重"分发**（不看连接数，看真实资源占用）。
- 为**重任务（转码/推理）单独设工作队列**，别和 web 入口混在同一批副本上调度。
- 给容器设**资源上限（requests/limits）**，避免单 pod 吃掉整节点。

### 第二层 · 代码层（治标，需开发配合）
- **单用户并发上限**：同一用户同时进行的重任务不超过 N 个，超出排队。
- **单请求大小上限**：单次请求的视频时长/分辨率/文件体积设硬上限，超限直接拒绝并提示。
- **大任务异步化**：入口只负责"收单入队"，立刻返回，不让请求阻塞在入口。

### 第三层 · 架构层（治本，成本最高）
- **重活轻活分离**：web 层只做接收与鉴权；转码/推理放到独立的 worker 集群，用消息队列（Kafka/RabbitMQ/Redis Stream）**削峰填谷**。
- worker 集群按队列长度**独立扩缩容**，与入口解耦。

**给用户的一句话结论模板**：
> "你这台被打满，根因是〔A/B/C 组合〕。**今天可以先做**〔配置层动作〕顶住；**中期**让开发加〔代码层动作〕；**长期**建议把重任务拆成独立 worker 集群（架构层）。"

### 紧急止血（若正在出事）
1. 手动把被打满的副本**从负载均衡摘除**，让流量分到其他副本；
2. 对该"异常用户/来源"**临时限流或封禁**；
3. 若已 OOM，**调大 limit 或迁移该 pod**，先恢复服务，再谈根因。

---

## 4. 与"资源画像"联动：该加机器还是该改架构？

诊断的下一步常是"那我该买多大机器 / 加几个节点？"。此时**不要凭空估算**，转入 `resource-profiling` 流程：

- **找出单请求峰值**：实测一个典型重请求吃多少内存、多少 CPU（这决定"单节点最多同时扛几个重任务"）。
- **算安全水位**：用实测峰值的 **60%~70%** 作为单节点推荐运营水位，反推所需节点数。
- **明确写出**："推荐值基于**实测峰值**，不是估算；突发业务的实际流量依赖用户行为，无法静态预测。"

**对突发型业务（视频/AI 推理）的标准话术**：
> "这类业务我**不做凭空预测**，我给你的是**实测临界点 + 安全水位**：单请求峰值 X GB，单节点安全并发 Y，超过会 OOM。请以实测为准。"

## 5. 输出报告结构（固定三块）

```
【一、实测事实】（可信）
  - 各副本：请求数 / CPU / 内存(RSS) / 重启次数 / OOM 记录
  - 入口负载均衡算法与会话保持设置
  - 结论：请求数与资源占用是否匹配

【二、根因判定】（推断，附依据与置信度）
  - 判定：A 会话粘性 / B 单请求过重 / C 缺限流（可多选）
  - 依据：〔引用的具体实测数据〕
  - 置信度：高 / 中 / 低
  - 未验证假设：〔列出需要用户确认的信息，如节点是否同物理机、是否共享内存带宽〕

【三、处置建议】（分层）
  - 止血（若在故障中）
  - 配置层 → 代码层 → 架构层，各附成本与见效速度
  - 若涉及容量：附实测峰值 + 安全水位 + 风险提示
```

## 6. 严格禁止（护栏）

- **禁止**把推断说成事实。凡无实测支撑的结论，必须标"推断/低置信度"。
- **禁止**在没确认环境的情况下给出"对生产环境执行压测"的建议；任何压测须 `mode=confirm` + 时长上限 + 一键中止。
- **禁止**暗示本诊断能"精准预测"突发业务流量——只给实测临界点与安全水位。
- **禁止**贬低开发、把责任简单甩给某一方；分层给建议，让用户按成本选。
- **禁止**在报告中泄露其他用户/租户的隐私数据；采样日志须脱敏。
