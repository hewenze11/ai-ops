# 告警接入与结果外推（Alertmanager 集成）

更新：2026-10-04。用户设计要求（2026-10-04，多轮讨论定稿）：

> 我们不抢成熟运维产品的活，而是在它们之上叠加。告警的第一时间由
> **Alertmanager** 负责（那是它做了十年的强项），我们做**第二棒**：
> 拿到告警后让 AI 排查，**把"排查结论"而不是"原始告警"回推给用户**。

## 一、为什么是这个定位（设计哲学）

告警系统最难的三件事是**实时性、可靠性、风暴限流**。这些 Alertmanager
已经做得很好了。我们**不碰**这三件事，只补它补不了的那一厘米：

- **这是什么**（告警归类：web-api / db / cache / 网络…）
- **最可能的原因**（AI 归因 + 置信度）
- **建议动作**（要不要动、动什么、风险多大）
- **如果告警在分析期间已恢复** → 明确说明"疑似瞬时抖动，已恢复"

因此：**慢 1–2 分钟完全没关系**，因为"快"的那部分 Alertmanager 已经做了。
我们是"告警的第二大脑"，不是"告警通道"。

**推论（重要）**：既然第一棒已经通知了用户，我们**不做**"高危事件抢在
Alertmanager 之前喊一嗓子"——那是噪音，不是价值。我们只在 AI 分析完成后
推一条"更有判断力的东西"。这正是"合作而非取代"。

## 二、数据流

```
监控系统 (Prometheus/其他)
      │  firing / resolved
      ▼
 Alertmanager ──────────► (第一时间：原始告警) ──────────► 用户（现有渠道）
      │
      │  webhook（同一份告警，POST 到主服务）
      ▼
 主服务 /api/v1/triggers/{id}/invoke
      │  1. 写入内置告警日志 alarm_log（含重复/被拒也算）
      │  2. 落 trigger_events，驱动角色轮次
      ▼
 AI 排查（按告警配置里选定的「AI 行为」执行）
      │  只读分析 / 直接处理 / 匹配简单规则
      ▼
 结果外推：把「排查结论」POST 到用户配置的 Webhook URL
      │  飞书 / 钉钉 必做，另尽量多填充常见渠道
      ▼
 用户（约 1–2 分钟后收到 AI 结论，与第一条告警对照）
```

## 三、AI 行为可选（原生支持，已落地）

告警配置（定制任务）里，用户可选 AI 遇到告警后做什么：

| 取值 | 语义 |
|---|---|
| `readonly` | **只读分析**：只排查、只给结论，绝不改任何机器 |
| `confirm` | 排查后若要动手，**先经人工审批**再执行 |
| `direct` | 排查后**直接处理**（用户已显式授权该风险） |
| 规则匹配 | 简单/常见告警只读处理，复杂问题才交给 AI（由 prompt/路由表达） |

控制权在**用户**手里：保守的选只读，激进的选直接处理。**"AI 的手能伸多长"
由用户决定**，这是产品最硬的信任基石。（底层即现有 `mode` 语义。）

## 四、去重边界（不重造轮子，但有底线）

- Alertmanager 自身有 `group_interval / repeat_interval`，它**会**去重。
- **前提是用户配好了**。用户配得糙时，它会把同一事件的原始告警重复推来。
- 因此我们**不做全量去重**（那是重造轮子），但**必须有一个极简指纹去重**：
  同一 `groupKey` / `X-Event-ID` 在时间窗内**只分析一次**，其余记
  `duplicate` 日志但不重复触发、不重复外推。
- 这是**防御性的**，不是替用户的配置错误买单。

## 五、处理 `resolved`（额外价值点）

Alertmanager 会推 `firing`，也会推 `resolved`。我们**必须处理 `status: resolved`**：

- 若告警在 AI 排查期间就恢复了 → 结论变为
  **"该问题在分析期间已自动恢复，判断为瞬时抖动"** —— 这条比"还在报警中"更值钱。
- 推送时显式区分 `firing` / `resolved`，让用户一眼看出当前状态。

## 六、外推推送包含哪些字段

推的是**结论**，不是原始告警。字段建议：

1. **标题**：`[已分析] <原告警标题>`（一眼区分于 Alertmanager 的原始告警）
2. **这是什么**：告警归类
3. **最可能的原因**：AI 归因 + 置信度（高/中/低）
4. **建议动作**：要不要动、动什么、风险多大
5. **当前状态**：`firing` / `resolved`（已恢复/疑似抖动）
6. **回指 Alertmanager 那条**：带上 fingerprint / 原始标题，方便对照

> 主动承认自己是"第二棒"、并引用 Alertmanager 的原始告警，不仅不丢人，
> 反而显得专业：用户会觉得"这套东西是懂 Alertmanager 的人做的"。

## 七、渠道适配

用户只需在主服务里**填一个 Webhook URL**。飞书/钉钉/企微/Slack 等机器人
本质都是"你 POST 一个 JSON 到某个 URL"，所以一次功能覆盖所有主流 IM，
且**零渠道 SDK 适配成本**——渠道改政策是用户的事。

**内置模板（payload 结构不同，自动适配）：**

| 渠道 | 识别方式 | JSON 形状 |
|---|---|---|
| 飞书 (Feishu/Lark) | URL 含 `open.feishu.cn` / `larksuite.com` | `{"msg_type":"text","content":{"text":...}}` 或卡片 |
| 钉钉 (DingTalk) | URL 含 `oapi.dingtalk.com` | `{"msgtype":"markdown","markdown":{"title":...,"text":...}}` |
| 企业微信 (WeCom) | URL 含 `qyapi.weixin.qq.com` | `{"msgtype":"markdown","markdown":{"content":...}}` |
| Slack | URL 含 `hooks.slack.com` | `{"text":...}` |
| Discord | URL 含 `discord.com/api/webhooks` | `{"content":...}` |
| 通用 (generic) | 其它 | 结构化 JSON（我们自己定义，附 `text` 字段） |

渠道识别**只按 URL 主机名匹配**，匹配不到一律走 `generic`（不瞎猜）。

## 八、安全底线（**不算过度设计**）

> 原则："皮实耐用"砍的是花哨功能，**不能**砍安全底线。

用户填 Webhook URL，由我们的服务去 POST。**必须**：

1. **SSRF 防护**：拒绝内网/回环/链路本地地址（`127.0.0.0/8`、`10/8`、
   `172.16/12`、`192.168/16`、`169.254/16`、`::1`、`fc00::/7`、`fe80::/10` 等），
   拒绝 `file:` 等非 http(s) 协议，解析主机名后再校验**任一**解析地址落在黑名单即拒。
   否则用户（或攻击者）填 `http://169.254.169.254/`（云元数据）会让服务器吐出云凭证。
2. **超时**：连接与读取都要有超时，避免外推线程卡死。
3. **响应大小上限**：只读少量响应体。
4. **失败有日志**：外推失败要可观测（但**不**记录密钥、**不**回显完整 URL 里的 token）。
5. **不做**：多渠道 SDK、复杂重试编排、消息模板引擎、可视化配置器 —— 这些才是过度设计。

### 判断某功能是否该做（三问）

1. 不做会不会出**安全问题**？→ 是，必做（哪怕简单）。
2. 不做用户是不是**完全没法用**？→ 是，必做。
3. 做了体验更好但不做也能用？→ **这才**用"皮实耐用"砍。

## 九、外推的持久化与可靠性（最小实现）

不做复杂编排，但**不能丢**：

- 外推以**持久化 outbox** 记录（`alert_notifications` 表），一行一次外推。
- 后台 worker 取 `pending` 行投递；成功置 `delivered`；失败按**有界退避**重试
  若干次后置 `failed`（保留最近错误类型，不落密钥）。
- 相同 `dedupe_key` 已有 `delivered`/`pending` 行 → 不重复外推。
- 进程重启后 `pending` 行继续投递（与定时任务 outbox 同思路）。

## 十、API

（均需管理员，除注入端点用触发 token / 内部鉴权）

- `PUT /api/v1/alert-notify/config`：设置外推目标
  `{"url": "...", "enabled": true, "channel": "auto|feishu|dingtalk|wecom|slack|discord|generic"}`
  返回时 **URL 中的敏感 query 参数打码**。
- `GET /api/v1/alert-notify/config`：读取当前配置（URL 打码）。
- `DELETE /api/v1/alert-notify/config`：停用并清除。
- `POST /api/v1/alert-notify/test`：发一条测试推送（验证 URL 通不通）。
- `GET /api/v1/alert-notify/deliveries`：外推投递记录（游标分页）。
- 外推内容来自**角色轮次完成后的 `final_text`**；告警上下文由
  `custom_task_id` / `X-Event-ID` 关联。

## 十一、与既有模块的关系

- **alarms.py**：内置告警日志（已存在）。本功能在其上增加"**结果外推**"，
  不改其默认落日志语义。
- **custom_tasks.py**：告警入口与 AI 行为（mode）。本功能复用其触发端点。
- **channels.py**：面向"聊天身份"的消息通道（被动回复）。本功能面向
  "告警结果外推"（主动推送），两者独立；共同点是都**只对接协议，不对接 SDK**。
- **turns.py**：轮次完成后 `final_text` 是外推内容来源；在外推 worker 里
  按 `turn_id` 取，不侵入模型主循环。

## 十二、边界与不做的事

- **不做**：替换 Alertmanager 的去噪/分组/静默；不做告警优先级/抢占仲裁。
- **不做**：渠道 OAuth / 应用注册 / 消息回执。
- **不做**：保证"必达"——这是尽力外推，失败可见即可；第一棒已由 Alertmanager 兜底。
- 零基础用户不会配 webhook？→ 由**课程**教会他们配（产品边界之外）。

## 十三、测试计划

`tests/test_alert_webhook.py`：

1. 配置外推 URL，channel 自动识别（飞书/钉钉/企微/Slack/Discord/generic）。
2. 轮次完成后生成外推行，字段含"已分析/原因/建议/状态"。
3. `dedupe_key` 去重：同一告警不重复外推。
4. `resolved` 状态被正确处理并体现在文案里。
5. **SSRF**：内网/回环/链路本地/非 http(s) → 配置被拒；解析到内网 → 拒。
6. 外推失败：有界重试后置 `failed`，错误类型可读，**不含密钥**。
7. URL 含 token 的 query 在 GET 返回里被**打码**。
8. 测试推送端点工作。
