# 定制任务：触发任务 / 定时任务

用户已确认：原「触发任务」页面入口改名为「定制任务」，包含触发任务、定时任务两类；共同编辑角色、提示词、执行账号与执行模式，定时任务增加Linux风格时间配置。Web尚未开发，本次实现对应后端。

## 编辑模型

`POST /api/v1/custom-tasks` 创建；`PUT /api/v1/custom-tasks/{id}` 全量编辑；`GET` 列表/单条；`DELETE` 停用并软删除（保留全部已接受事件和审计）。以上需要管理员凭据。

```json
{
  "id": "daily-inspection",
  "name": "每日早间巡检",
  "kind": "scheduled",
  "role_id": "ops",
  "prompt": "检查注册的生产资产，输出异常及建议；不猜测资产身份。",
  "execution_users": ["ops_read"],
  "mode": "confirm",
  "enabled": true,
  "cron": "0 9 * * *",
  "timezone": "Asia/Shanghai"
}
```

触发任务使用 `kind=trigger`、`cron=null`。每条定义生成自己的trigger路径和独立随机Token，明文只在创建响应返回一次，数据库保存哈希。定时任务也可经同一入口手动触发；两类共享模板，不把提示词当shell命令。

## Cron 时间编辑

格式：`分 时 日 月 周`，不含命令，不是包含用户名/命令的完整crontab行。支持 `*`、列表、范围、步长以及月份/星期缩写；不支持秒、年份、`@daily`、`?`、`L`、`W`、`#` 等扩展。

- `*/5 * * * *`：每5分钟。
- `0 9 * * *`：每天09:00。
- `30 2 * * 1-5`：周一至周五02:30。
- `0 3 1 * *`：每月1日03:00。
- 周日可写0或7；日期和星期同时限制时按传统Cron的“或”匹配，不是“且”。

时区使用IANA名称，默认Asia/Shanghai，不依赖服务器当前时区。数据库时间使用UTC时间戳；预览展示含UTC偏移的本地时间。夏令时不存在的本地时间跳过；重复本地时间只取第一次。本实现有对应自动测试，不能直接采用库在DST边界的隐式补时行为。

`POST /api/v1/custom-tasks/cron-preview`，示例输入 `{"cron":"0 9 * * *","timezone":"Asia/Shanghai","count":5}`，返回后续触发时刻。非法或不可能的日期返回422。

## 统一触发接口

`POST /api/v1/triggers/{custom_task_id}/invoke`

- Bearer Token：该条定义的trigger凭据，或服务内部管理员凭据。
- JSON body：原始告警/事件对象，作为数据保存；不能覆盖模板中的角色、账号或模式。
- 可选 `X-Event-ID`：告警源稳定事件ID，用于该定制任务内去重。相同ID和相同正文返回同一事件；同ID不同正文409。没有ID则每次均为新事件。
- 正文暂限256KiB；不接受数组或任意可执行正文。
- 返回202：`accepted=true, event_id=..., state=queued`。这里的accepted只表示可靠落盘，不代表AI已执行。

定时器不直接调用执行Agent。流程如下：
1. 查到期Cron配置，事务内生成持久化投递箱记录，并保存配置修订/提示词/账号快照。
2. 定时器经固定的本机HTTP地址调用上述trigger接口，使用稳定的内部调度事件ID。
3. trigger接口将事件与配置快照写入角色待处理队列，再应答。
4. 回执丢失时重试同一事件ID，只保留一条输入，不重复生成角色任务。

`X-Schedule-Event-ID` 仅服务内部凭据可用；外部触发Token不能伪造调度身份。发送目标固定为本服务回环地址，不允许传任意目标URL，也不跟随带认证的重定向。

## 当前实现边界

- 已做到：到点 → HTTP trigger → 角色输入落盘/日志/重试去重。
- dev3已增加模型消费者，并与手工单命令、聊天输入统一为角色轮次队列。需配置供应商并显式启用角色模型；模型处理与权限边界见model-turns.md。尚不代表成熟运维诊断策略已完成。
- 严禁将提示词直接作为 `/bin/sh -c` 参数。执行Agent协议保持1.0，不因新增调度功能升级或改造Agent。
- `GET /api/v1/custom-task-events` 查询事件/原始payload/配置快照，可按role_id和游标查询。
- `GET /api/v1/schedule-deliveries` 查看投递状态、次数、错误类型及关联事件ID。

## 工程默认值（预览版，可后续调整）

- 已持久化但未投递的事件：重启后继续重试，指数退避，最长间隔300秒。
- 停机期间漏掉、尚未生成记录的时刻：超过60秒宽限后跳过，写审计并计算未来下一次；不默认补发成百上千条历史任务。
- 该规则是工程默认值，不是用户已要求“永远不补跑”；后续如增加补跑策略，应显式配置。
- 修改配置影响未来生成的事件；已经生成的投递保留原角色/账号/提示词快照。
- 停用或删除：取消尚未投递的记录，不删除已接受事件，也不取消已经开始的AI任务；轮次取消是独立控制操作。
- 定时任务不会自动抢占角色。消费者按角色轮次串行处理，仍由用户安排专用角色。
- 调度不承诺硬实时、exactly-once执行或对第三方系统的操作幂等；当前保证的是触发输入的幂等接受。

## 数据迁移

定制任务最初使用schema2；dev3的schema3进一步加入统一角色轮次、模型调用和文档表。迁移事务化，不删除原角色/资产/任务/审计。升级前备份SQLite需使用SQLite backup API或停服务复制，不能在WAL运行时仅复制主文件。旧版本不认识新schema，不能仅换旧镜像回滚；需恢复匹配的升级前备份。
